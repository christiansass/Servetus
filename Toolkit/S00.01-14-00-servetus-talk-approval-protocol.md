# Servetus Talk Approval Protocol

## Purpose

Provide a sovereign, auditable, multi-party approval mechanism for high-trust
actions — built entirely on Nextcloud Talk with no external dependencies.

The Talk conversation IS the audit trail. No separate compliance dashboard.
No third-party auth service. No Okta, no Auth0. Runs on your infrastructure.

---

## When This Protocol Applies

Any action that meets one or more of these conditions:

- Irreversible (delete, overwrite, deploy, send)
- Affects shared infrastructure (config changes, service restarts, user creation)
- Financial (above a configurable threshold)
- Cross-client (any action touching more than one client's data)
- Explicitly flagged as requiring approval in a spec or project file

Servetus checks these conditions before acting. If any applies, it routes
through this protocol rather than proceeding unilaterally.

---

## The Flow

```
1. Servetus identifies a high-trust action needed

2. Servetus creates or opens the approval room
   - Permanent room for standing approvals (e.g. "Infrastructure Approvals")
   - Or temporary room for one-off decisions

3. Servetus posts the action proposal clearly:
   "ACTION REQUIRED: Deploy new Whisper model to gpu-node
    Requestor: Servetus
    Reason: Faster transcription for new recording format
    Impact: 10 min service interruption, transcription queue pauses
    Requires: [vault-owner] + collaborator-b collaborator-e
    Deadline: None (pending approval)"

4. Servetus generates one-time tokens — one per required approver
   - Cryptographically random (32 hex chars)
   - Single-use, expire in 24 hours
   - Never reused

5. Servetus delivers tokens out-of-band:
   - Email to approver's address on file
   - OR SMS to approver's number on file
   - OR both (configurable per action tier)
   - Token is NEVER posted in the Talk room

6. Each approver pastes their token in the room:
   "APPROVE: a3f8c2d1e9b4..."

7. Servetus validates each token server-side:
   - Correct token for this approver
   - Not expired
   - Not previously used
   - Posted by the correct Nextcloud user

8. Quorum reached → action executes
   Servetus posts: "APPROVED by [names] at [timestamps]. Executing."

   Any rejection → action blocked
   Servetus posts: "REJECTED by [name] at [timestamp]. Action cancelled."
   Servetus notifies all participants.
```

---

## Two-Factor by Design

The protocol is inherently two-factor:

**Factor 1** — You are in the Talk room (you have your Nextcloud credentials)
**Factor 2** — You have access to your email or phone (you received the token)

Both must be true to approve. Compromising one factor is not enough.

---

## Quorum Models

Configurable per action type:

| Model | Description | Use case |
|-------|-------------|----------|
| `unanimous` | All named approvers must approve | High-stakes irreversible actions |
| `majority` | More than half must approve | Standard governance |
| `any-one` | First approver to respond unblocks | Time-sensitive, lower-risk |
| `named` | Specific named individuals only | Role-based (CTO must approve infra) |

---

## The Audit Trail

The Talk room log contains:
- The action proposed (full details, timestamped)
- Who was required to approve
- When each token was delivered (logged, not the token itself)
- When each approver responded
- The final outcome (approved/rejected)
- What was executed (or that execution was cancelled)

This log is human-readable without any special tooling. It can be exported,
searched, or referenced in any compliance review. It never requires a
third-party system to interpret.

```python
import secrets, hashlib
from datetime import datetime, timedelta

def generate_token(action_id: str, approver_id: str) -> str:
    token = secrets.token_hex(32)
    # Store hash (not token) in state
    store_token_hash(
        action_id=action_id,
        approver_id=approver_id,
        token_hash=hashlib.sha256(token.encode()).hexdigest(),
        expires_at=datetime.now() + timedelta(hours=24)
    )
    return token  # Delivered out-of-band, never stored in plaintext

def validate_token(action_id: str, approver_id: str, submitted: str) -> bool:
    record = get_token_record(action_id, approver_id)
    if not record or record['used'] or datetime.now() > record['expires_at']:
        return False
    valid = hashlib.sha256(submitted.encode()).hexdigest() == record['token_hash']
    if valid:
        mark_token_used(action_id, approver_id)
    return valid
```

## Rejection Handling

A rejection does not just block the action. It triggers:

1. Action cancelled and logged
2. All approvers notified (even those who hadn't responded yet)
3. Rejecting approver's reason requested (optional, posted to room)
4. Requestor notified with full context

No action can be resubmitted for 1 hour after rejection without a new
justification posted to the room by the requestor.

## What This Replaces

| Old approach | This protocol |
|-------------|--------------|
| Email chains for approval | Talk room — all parties, all history, one place |
| DocuSign / e-signature | Token paste — same legal weight, zero vendor |
| Slack polls | Talk proposal — structured, auditable, actionable |
| Verbal sign-off | Written, timestamped, attributed record |
| Trust-based "I told them" | Cryptographic proof of approval |
