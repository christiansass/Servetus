# S00.01-04-00 — Servetus Talk Bot Service

## Purpose

This spec defines the architecture for **autonomous service bots** that operate within the Servetus ecosystem. Each bot is a Nextcloud user — authenticated with its own scoped credentials, restricted by Nextcloud's built-in permission model, and backed by a local LLM.

The bot is not the kernel. It is a **service with a local brain**. It receives instructions, translates intent into structured vault operations, and executes within the permissions Nextcloud grants it. The human remains the authority. The bot remains the servant.

### Interface Agnosticism

Talk is the **most convenient** interface — especially on mobile or when introducing a service into a group conversation for collaborative assistance — but it is not the only one. A bot service exposes its intent parser and executor through multiple channels:

| Interface | Use Case | How It Works |
|-----------|----------|--------------|
| **Nextcloud Talk** | Mobile, group conversations, casual commands | Bot polls Talk room, responds in-thread |
| **CLI** | Scripting, automation, local development | `servetus bot exec inbox "sort today's captures"` |
| **WebDAV triggers** | File-based automation | Bot watches a folder; new files trigger processing |
| **HTTP API** | Integration with other services | Bot exposes a local endpoint for structured requests |
| **Cron / scheduled** | Recurring tasks | Bot runs on a schedule (daily digest, weekly summary) |

The bot runtime is the same regardless of how it receives input. Talk is one mouth. The CLI is another. A cron job is another. The brain and hands are identical.

## Design Principles

1. **The bot is a Nextcloud user.** It authenticates the same way you do — username, app password. Nextcloud doesn't know it's a bot. This means all existing ACLs, share permissions, and audit logs apply without custom auth code.

2. **Permissions are Nextcloud's job.** The bot sees only what its Nextcloud account is allowed to see. Want to restrict it from witnesses? Don't share `01-witnesses/` with its account. Revoke access? Disable the user. No custom permission layer to build or maintain.

3. **Credentials never leave the sovereign tier.** The bot runs on a machine that logs into Nextcloud. The credentials live in a local config file on that machine. They never travel to a transient tier, never get committed to Git, never get pasted into a chat.

4. **Each service is its own entity.** Following the OpenClaw pattern — services are independent, deployable, scalable. One bot handles voice transcription. Another handles inbox triage. A third handles daily log synthesis. Each has its own Nextcloud account, its own permissions, its own LLM context.

5. **Local LLM first.** The bot's reasoning runs on local hardware. No API calls to external AI services unless explicitly escalated by the user. Phase 1 is a Llama model on consumer hardware. Phase 2 is dedicated inference hardware colocated with the server.

## Bot Runtime Components

Each bot runtime consists of three layers:

### 1. Talk Client

Extends the existing `TalkListener` from `00-system/nextcloud/talk.py`. The bot authenticates as its own Nextcloud user and polls (or receives webhooks from) a designated Talk room.

```python
# Bot authenticates with its OWN credentials — not the human's
bot_config = NextcloudConfig(
    url="https://cloud.example.com",
    username="servetus-bot-inbox",        # Dedicated bot account
    app_password="xxxxx-xxxxx-xxxxx",     # Scoped app password
    talk_room_token="abc123",             # Assigned room
    talk_poll_interval=3,
)
```

**Message flow:**
1. Human sends message in Talk room
2. Bot polls for new messages (reuses `TalkListener.get_new_messages()`)
3. Message text is passed to the Intent Parser
4. Response is sent back via `TalkListener.send_message()`

### 2. Intent Parser

Translates natural language from Talk into structured commands the vault executor understands. This is where the local LLM does its work.

```python
class IntentParser:
    """
    Takes a Talk message, runs it through a local LLM,
    and returns a structured intent.
    """

    def __init__(self, llm_backend: LLMBackend):
        self.llm = llm_backend

    def parse(self, message: str, context: dict) -> Intent:
        """
        Returns a structured intent from natural language.

        context includes:
        - actor: who sent the message
        - room: which Talk room
        - recent_messages: conversation history (bounded)
        - bot_role: what this bot is responsible for
        """
        ...
```

**Intent structure:**

```python
@dataclass
class Intent:
    action: str          # create | read | update | move | search | summarize | escalate
    target: str          # vault path, record type, or query
    parameters: dict     # action-specific parameters
    confidence: float    # 0.0–1.0, how sure the LLM is about the parse
    raw_message: str     # original Talk message (for audit)
    requires_confirm: bool  # True if action modifies vault state
```

**Confidence behavior:**
- `>= 0.9` — Execute (if non-destructive) or confirm and execute
- `0.7–0.9` — Confirm with user before executing, show parsed intent
- `< 0.7` — Ask for clarification, don't guess

**All write operations require confirmation by default.** The bot proposes, the human approves in Talk. This mirrors the sorting/placement protocol: "Detection is automatic. Placement is consensual."

### 3. Vault Executor

Executes confirmed intents against the vault filesystem via WebDAV or local file access (depending on where the bot runs).

```python
class VaultExecutor:
    """
    Executes structured intents against the Servetus vault.
    Respects Nextcloud permissions — if the bot's account
    can't access a path, the operation fails cleanly.
    """

    def __init__(self, webdav: WebDAVClient, vault_root: str):
        self.webdav = webdav
        self.vault_root = vault_root

    def execute(self, intent: Intent) -> ExecutionResult:
        """
        Run the intent. Returns success/failure + output.
        All write operations should have been confirmed
        before reaching this method.
        """
        ...
```

**Supported operations (Phase 1):**

| Action | Description | Modifies Vault? |
|--------|-------------|:---:|
| `read` | Read a file or list a directory | No |
| `search` | Search vault by keyword, tag, or date | No |
| `summarize` | Summarize a file, folder, or time range | No |
| `create` | Create a new record (log, event, etc.) | Yes |
| `update` | Edit an existing record | Yes |
| `move` | Move a record between folders | Yes |
| `escalate` | Flag for human review / defer to a higher-tier LLM | No |

## Nextcloud Permission Model

The bot's access is controlled entirely through Nextcloud:

### Account Setup

```
Nextcloud Admin Panel → Users → Create User
  Username: servetus-bot-inbox
  Group: servetus-bots
  Quota: 1 GB (or as needed)

Nextcloud Admin Panel → Files → Sharing
  Share specific folders with the bot account
  Set read-only or read-write per folder
```

### Example Permission Profiles

**Inbox Triage Bot** — sorts incoming captures into the right folders:
```
01-witnesses/     → Read-only (needs to read, not modify originals)
02-daily-logs/    → Read-write (creates/updates logs)
03-events/        → Read-write (files events from inbox)
04-projects/      → Read-only (reads project index for sort decisions)
06-radar/         → Read-only (checks what's being tracked)
```

**Daily Digest Bot** — summarizes the day's activity:
```
02-daily-logs/    → Read-write (creates digest)
03-events/        → Read-only (reads today's events)
06-radar/         → Read-only (checks active tracking)
```

**Voice Processing Bot** — transcribes and files voice recordings:
```
01-witnesses/     → Read-write (reads audio, writes transcripts)
02-daily-logs/    → Read-write (appends voice captures to log)
```

### Audit Trail

Every action the bot takes is visible in two places:
1. **Nextcloud Talk** — the conversation is the command log
2. **Nextcloud activity log** — file operations are tracked per-user

No custom audit system needed. Nextcloud already does this.

## Hardware Phases

### Phase 1 — Home PC (Current)

```
Hardware:
  - GPU: NVIDIA GTX 1080 Ti (11 GB VRAM)
  - RAM: 64 GB (or more)
  - Location: Home network

LLM:
  - Engine: llama.cpp or Ollama
  - Model: Llama 3 8B (Q4_K_M quantization fits in 11 GB VRAM)
  - Context: 8192 tokens (sufficient for Talk message + vault context)

Network:
  - Bot runs on home PC
  - Authenticates to Nextcloud over HTTPS
  - Same as logging in from your browser — just automated

Limitations:
  - Latency depends on home internet → Nextcloud server
  - GPU shared with other tasks (gaming, etc.)
  - Single point of failure (PC off = bot off)
```

### Phase 2 — Colocated Mac Minis

```
Hardware:
  - Apple Mac Mini M1 or M3
  - 16–32 GB unified memory
  - Location: Data center, same rack as Nextcloud server

LLM:
  - Engine: llama.cpp (Metal acceleration) or MLX
  - Model: Llama 3 8B or 70B (M3 with 32 GB can run larger models)
  - Context: 8192–32768 tokens

Network:
  - Local network to Nextcloud server
  - Sub-millisecond latency
  - Always-on, dedicated hardware

Advantages:
  - No home internet dependency
  - Dedicated inference hardware
  - Multiple Minis = multiple independent bots
  - Low power consumption (~10W idle per Mini)
```

### Phase 3 — Scaled Service Fleet

```
Each service instance:
  - Own Nextcloud user account
  - Own LLM context / system prompt
  - Own permission scope
  - Independently deployable

Scaling:
  - Need more throughput? Add a Mac Mini, create a user, deploy a bot
  - Need a new capability? Write a role prompt, create a user, deploy
  - Bot misbehaving? Disable the Nextcloud account. Immediate kill switch.
```

## Bot Configuration

Each bot has a local config file (never committed to Git):

```yaml
# config/bot-inbox.yaml — Sovereign tier only

identity:
  name: "servetus-bot-inbox"
  role: "Inbox triage and daily log management"
  description: "Sorts incoming captures, maintains daily logs"

nextcloud:
  url: "https://cloud.example.com"
  username: "servetus-bot-inbox"
  app_password: "xxxxx-xxxxx-xxxxx-xxxxx-xxxxx"
  talk_room_token: "abc123"
  talk_poll_interval: 3

llm:
  engine: "ollama"            # ollama | llama-cpp | mlx
  model: "llama3:8b-q4_K_M"
  context_length: 8192
  temperature: 0.3            # Low temp — we want precision, not creativity
  system_prompt_file: "00-system/bot-prompts/inbox-triage.md"

behavior:
  confirm_writes: true         # Always confirm before modifying vault
  confidence_threshold: 0.7    # Below this, ask for clarification
  max_message_history: 20      # Talk messages to include as context
  quiet_hours:                 # Don't initiate messages during these hours
    start: "22:00"
    end: "07:00"
    timezone: "America/Chicago"
```

## Bot System Prompt Pattern

Each bot gets a system prompt that defines its role. This is a Toolkit-adjacent file — it follows vault conventions but lives in `00-system/bot-prompts/`.

```markdown
# Inbox Triage Bot — System Prompt

You are a Servetus service bot responsible for inbox triage.

## Your Role
- Monitor incoming captures in the daily log
- Suggest filing locations for unsorted items
- Create event records when captures match event criteria
- Maintain the daily log structure

## Your Constraints
- You NEVER define what happened. The witnesses define what happened.
- You SUGGEST placement. The human CONFIRMS placement.
- You operate within the permissions granted to your Nextcloud account.
- You follow the Toolkit specs, especially:
  - Sorting and placement protocol (S00.01-01-20)
  - Frontmatter schema (S00.01-02-00)
  - Time rules (S00.01-02-10)

## Your Response Style
- Short, clear messages in Talk
- When suggesting an action: state what you'd do, wait for approval
- When reporting: state facts, cite the file path
- Never be verbose. This is a chat interface, not an essay.

## Escalation
- If confidence < 0.7, say so and ask for clarification
- If the request is outside your role, say "That's outside my scope"
- If the request requires sovereign-tier access you don't have, say so
```

## Talk Room Topology

Bots can be organized across Talk rooms in different patterns:

### Pattern A — Single Room (Simple)
```
#servetus (Talk room)
  ├── Human (you)
  ├── inbox-bot
  ├── digest-bot
  └── voice-bot

All bots see all messages. Each responds only to its domain.
Use @mentions to direct commands: "@inbox sort today's captures"
```

### Pattern B — Dedicated Rooms (Isolated)
```
#servetus-inbox    → Human + inbox-bot
#servetus-digest   → Human + digest-bot
#servetus-voice    → Human + voice-bot
#servetus-general  → Human only (or human + a general assistant)

Each bot sees only its room. Clean separation of concerns.
```

### Pattern C — Hybrid (Recommended for Phase 1)
```
#servetus          → Human + all bots (general commands, status)
#servetus-inbox    → Human + inbox-bot (triage-specific work)

Start simple. Split rooms as bot count grows.
```

### New CLI Commands

```
servetus bot start inbox          # Start the inbox triage bot (Talk + scheduled)
servetus bot start digest         # Start the daily digest bot
servetus bot stop inbox           # Stop a running bot
servetus bot status               # List running bots and their state
servetus bot list                 # List configured bots
servetus bot exec inbox "message" # Send a one-shot command to a bot (no Talk needed)
servetus bot api inbox --port 8401  # Start bot with local HTTP API endpoint
```

The `exec` command is significant — it means you can script bot operations from the terminal, pipe them into other tools, or call them from cron without Talk being involved at all. Talk is the conversational interface. CLI is the programmatic one. Same bot, same brain.

## Security Model

### Authentication
- Each bot uses a **scoped Nextcloud app password** (not the main password)
- App passwords can be revoked instantly from the Nextcloud admin panel
- No OAuth complexity — Nextcloud's app password model is sufficient for Phase 1

### Authorization
- Nextcloud ACLs control file access per-user
- Talk room membership controls message visibility
- Bot group membership can be managed centrally

### Kill Switch
- Disable the Nextcloud user account → bot immediately loses all access
- No special kill switch infrastructure needed
- Works even if the bot's host machine is unreachable (it just can't auth on next poll)

### Credential Storage
- Bot config files live in `config/` (gitignored, Sovereign tier only)
- Credentials never appear in Talk messages, Git, or logs
- If a credential is accidentally exposed in Talk, rotate the app password immediately

## Relationship to Local AI Router

The local AI router (when implemented) sits below the bot service layer. The router decides which LLM backend to use; the bot service calls the router instead of calling `ollama` directly. This allows:

- Automatic model selection based on task complexity
- Fallback from local LLM to cloud API (with user consent)
- Shared model loading across multiple bots on the same machine

For Phase 1, the bot calls the LLM engine directly. Router integration comes later.

## What This Is Not

- **Not a chatbot.** The bot doesn't make small talk. It processes commands and reports results.
- **Not autonomous.** Write operations require human confirmation. The bot proposes, the human disposes.
- **Not Talk-only.** Talk is the most natural interface for mobile use and group conversations — you can pull a bot into a discussion and get real-time assistance. But the bot service runs independently of Talk. It can be driven by CLI, cron, file triggers, or API calls. Talk is the mouth you'll use most. It's not the only mouth.
- **Not a replacement for the kernel.** The LLM inside the bot handles intent parsing and simple reasoning. Complex synthesis, cross-arc analysis, and editorial judgment remain with higher-tier models (Claude, etc.) accessed through explicit escalation.
- **Not cloud-dependent.** The entire stack runs on hardware you own, connected to a server you control. If your internet goes down, the colocated bots keep working.
