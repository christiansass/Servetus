# S00.01-04-00 — Servetus Talk Bot Service

## Purpose

This spec defines the architecture for a **personal assistant service** that operates within the Servetus ecosystem. The assistant is a Nextcloud user — authenticated with its own scoped credentials, restricted by Nextcloud's built-in permission model, and backed by a local LLM.

The end goal: **you should never need to hire a human assistant.** This is your copilot, your secretary, your aide-de-camp. It manages your calendar, tracks your tasks, knows your contacts, files your records, and does it all within infrastructure you own. You should be able to converse with it naturally — not bark commands at a terminal.

### The RIO Model

Think of the F-14 Tomcat. The pilot flies the aircraft. The RIO (Radar Intercept Officer) sits behind them with full situational awareness — radar, weapons systems, navigation, communications. The pilot doesn't have to track everything because the RIO is covering the blind spots.

That's this assistant. You're the pilot. The assistant is your RIO:

- **Situational awareness** — knows your calendar, your active projects, your open tasks, what's on radar
- **Covers your blind spots** — especially where ADD creates gaps in context-switching, follow-through, and time management
- **Sits quietly in meetings** — listening, taking notes, extracting action items, filing them to the right projects
- **Post-call processing** — goes over transcripts, pulls out appointments, tasks, decisions, and sorts them by project and arc
- **Context maintenance** — remembers what you need to be doing in different places at different times, so you don't have to hold it all in your head
- **Proactive but not intrusive** — surfaces what's relevant when it's relevant, doesn't interrupt when you're in flow

The RIO doesn't fly the plane. The RIO makes the pilot effective.

The assistant is not the kernel. It is a **service with a local brain**. It receives instructions through conversation, translates intent into actions across Nextcloud's full PIM surface, and executes within the permissions granted to it. The human remains the authority. The assistant remains the servant — but a servant you trust, rely on, and want to work with.

### Nextcloud Is Not a File Server

The first draft of this spec treated Nextcloud as a file store. That was wrong. Nextcloud is a **full personal information management platform**:

| Service | Protocol | What It Does |
|---------|----------|--------------|
| **Files** | WebDAV | Document storage, vault sync |
| **Calendar** | CalDAV | Appointments, scheduling, availability |
| **Contacts** | CardDAV | People, organizations, relationships |
| **Tasks** | CalDAV (VTODO) | To-do lists, deadlines, priorities |
| **Talk** | REST API | Messaging, voice/video, group conversations |
| **Mail** | IMAP/SMTP | Email (if Nextcloud Mail is installed) |
| **Deck** | REST API | Kanban boards, project tracking |
| **Notes** | REST API | Quick capture, scratch space |
| **Notifications** | REST API | Alerts, reminders, bot-initiated nudges |

The assistant operates across **all of these**, not just files. "Schedule a meeting with David on Thursday" is a CalDAV operation. "Remind me to call the insurance company" is a task. "What's on my plate this week?" crosses calendar, tasks, and deck. The vault is the memory. Nextcloud's PIM services are the hands.

### Interface Agnosticism

Talk is the **most convenient** interface — especially on mobile or when introducing a service into a group conversation for collaborative assistance — but it is not the only one. A bot service exposes its intent parser and executor through multiple channels:

| Interface | Use Case | How It Works |
|-----------|----------|--------------|
| **Nextcloud Talk** | Mobile, group conversations, casual commands | Bot polls Talk room, responds in-thread |
| **CLI** | Scripting, automation, local development | `servetus bot exec inbox "sort today's captures"` |
| **WebDAV triggers** | File-based automation | Bot watches a folder; new files trigger processing |
| **HTTP API** | Integration with other services | Bot exposes a local endpoint for structured requests |
| **Cron / scheduled** | Recurring tasks | Bot runs on a schedule (daily digest, weekly summary) |

The bot runtime is the same regardless of how it receives input. Talk is one mouth. The CLI is another. A cron job is another. The brain and hands are identical.

## Design Principles

1. **The bot is a Nextcloud user.** It authenticates the same way you do — username, app password. Nextcloud doesn't know it's a bot. This means all existing ACLs, share permissions, and audit logs apply without custom auth code.

2. **Permissions are Nextcloud's job.** The bot sees only what its Nextcloud account is allowed to see. Want to restrict it from witnesses? Don't share `01-witnesses/` with its account. Revoke access? Disable the user. No custom permission layer to build or maintain.

3. **Credentials never leave the sovereign tier.** The bot runs on a machine that logs into Nextcloud. The credentials live in a local config file on that machine. They never travel to a transient tier, never get committed to Git, never get pasted into a chat.

4. **Each service is its own entity.** Following the OpenClaw pattern — services are independent, deployable, scalable. One bot handles voice transcription. Another handles inbox triage. A third handles daily log synthesis. Each has its own Nextcloud account, its own permissions, its own LLM context.

5. **Local LLM first.** The bot's reasoning runs on local hardware. No API calls to external AI services unless explicitly escalated by the user. Phase 1 is a Llama model on consumer hardware. Phase 2 is dedicated inference hardware colocated with the server.

## Bot Runtime Components

Each bot runtime consists of three layers:

### 1. Talk Client

Extends the existing `TalkListener` from `00-system/nextcloud/talk.py`. The bot authenticates as its own Nextcloud user and polls (or receives webhooks from) a designated Talk room.

```python
# Bot authenticates with its OWN credentials — not the human's
bot_config = NextcloudConfig(
    url="https://cloud.example.com",
    username="servetus-bot-inbox",        # Dedicated bot account
    app_password="xxxxx-xxxxx-xxxxx",     # Scoped app password
    talk_room_token="abc123",             # Assigned room
    talk_poll_interval=3,
)
```

**Message flow:**
1. Human sends message in Talk room
2. Bot polls for new messages (reuses `TalkListener.get_new_messages()`)
3. Message text is passed to the Intent Parser
4. Response is sent back via `TalkListener.send_message()`

### 2. Intent Parser

Translates natural language from Talk into structured commands the vault executor understands. This is where the local LLM does its work.

```python
class IntentParser:
    """
    Takes a Talk message, runs it through a local LLM,
    and returns a structured intent.
    """

    def __init__(self, llm_backend: LLMBackend):
        self.llm = llm_backend

    def parse(self, message: str, context: dict) -> Intent:
        """
        Returns a structured intent from natural language.

        context includes:
        - actor: who sent the message
        - room: which Talk room
        - recent_messages: conversation history (bounded)
        - bot_role: what this bot is responsible for
        """
        ...
```

**Intent structure:**

```python
@dataclass
class Intent:
    action: str          # e.g. "cal.create", "task.list", "intake.capture", "brief.morning"
    service: str         # files | calendar | contacts | tasks | deck | notify | cross
    target: str          # specific resource, query, or context
    parameters: dict     # action-specific parameters
    confidence: float    # 0.0–1.0, how sure the LLM is about the parse
    raw_message: str     # original message (for audit)
    requires_confirm: bool  # True if action modifies state
    sub_intents: list    # For cross-service ops — one message, multiple actions
```

A single message like *"I talked to David, he's in — set up a meeting next Tuesday at 10"* produces:

```python
Intent(
    action="intake.capture",
    service="cross",
    confidence=0.88,
    sub_intents=[
        Intent(action="file.create", service="files", target="03-events/", ...),
        Intent(action="cal.create", service="calendar", target="next Tuesday 10am", ...),
        Intent(action="contact.note", service="contacts", target="David", ...),
    ]
)
```

**Confidence behavior:**
- `>= 0.9` — Execute (if non-destructive) or confirm and execute
- `0.7–0.9` — Confirm with user before executing, show parsed intent
- `< 0.7` — Ask for clarification, don't guess

**All write operations require confirmation by default.** The bot proposes, the human approves in Talk. This mirrors the sorting/placement protocol: "Detection is automatic. Placement is consensual."

### 3. PIM Executor

Executes confirmed intents against the full Nextcloud PIM surface — not just files, but calendar, contacts, tasks, deck, mail, and notifications.

```python
class PIMExecutor:
    """
    Executes structured intents against Nextcloud services.
    Operates through standard protocols (CalDAV, CardDAV, WebDAV, REST).
    Respects Nextcloud permissions per-service.

        self.webdav = WebDAVClient(config)       # Files
        self.caldav = CalDAVClient(config)        # Calendar + Tasks
        self.carddav = CardDAVClient(config)      # Contacts
        self.deck = DeckClient(config)            # Boards / projects
        self.talk = TalkClient(config)            # Messaging
        self.notify = NotificationClient(config)  # Alerts

    def execute(self, intent: Intent) -> ExecutionResult:
        """
        Route intent to the appropriate Nextcloud service.
        All write operations should have been confirmed
        before reaching this method.
        """
        ...
```

## Nextcloud Permission Model

The bot's access is controlled entirely through Nextcloud:

### Account Setup

```
Nextcloud Admin Panel → Users → Create User
  Username: servetus-bot-inbox
  Group: servetus-bots
  Quota: 1 GB (or as needed)

Nextcloud Admin Panel → Files → Sharing
  Share specific folders with the bot account
  Set read-only or read-write per folder
```

### Example Permission Profiles

**Primary Copilot** — your main assistant, broad access:
```
Files:
  01-witnesses/     → Read-only (reads evidence, never modifies originals)
  02-daily-logs/    → Read-write (creates/updates logs)
  03-events/        → Read-write (files events)
  04-projects/      → Read-write (manages project records)
  06-radar/         → Read-write (updates tracking)
Calendar:            → Read-write (schedules, reschedules, cancels)
Contacts:            → Read-write (lookups, notes, new contacts)
Tasks:               → Read-write (creates, completes, defers)
Deck:                → Read-write (manages boards and cards)
Talk:                → Read-write (converses, reports, confirms)
Notifications:       → Write (sends reminders and alerts)
```

**Specialist — Voice Processing:**
```
Files:
  01-witnesses/     → Read-write (reads audio, writes transcripts)
  02-daily-logs/    → Read-write (appends voice captures)
```

**Specialist — Daily Digest:**
```

  02-daily-logs/    → Read-write (creates digest)

  06-radar/         → Read-only

```

### Audit Trail

Every action the bot takes is visible in two places:
1. **Nextcloud Talk** — the conversation is the command log
2. **Nextcloud activity log** — file operations are tracked per-user

No custom audit system needed. Nextcloud already does this.

## Hardware Phases

### Phase 1 — Home PC (Current)

```
Hardware:
  - GPU: NVIDIA GPU (11 GB VRAM)
  - RAM: 64 GB (or more)
  - Location: Home network

LLM:
  - Engine: llama.cpp or Ollama
  - Model: Llama 3 8B (Q4_K_M quantization fits in 11 GB VRAM)
  - Context: 8192 tokens (sufficient for Talk message + vault context)

Network:
  - Bot runs on home PC
  - Authenticates to Nextcloud over HTTPS
  - Same as logging in from your browser — just automated

Limitations:
  - Latency depends on home internet → Nextcloud server
  - GPU shared with other tasks (gaming, etc.)
  - Single point of failure (PC off = bot off)
```

### Phase 2 — Colocated Mac Minis

```
Hardware:
  - Apple Mac Mini M1 or M3
  - 16–32 GB unified memory
  - Location: Data center, same rack as Nextcloud server

LLM:
  - Engine: llama.cpp (Metal acceleration) or MLX
  - Model: Llama 3 8B or 70B (M3 with 32 GB can run larger models)
  - Context: 8192–32768 tokens

Network:
  - Local network to Nextcloud server
  - Sub-millisecond latency
  - Always-on, dedicated hardware

Advantages:
  - No home internet dependency
  - Dedicated inference hardware
  - Multiple Minis = multiple independent bots
  - Low power consumption (~10W idle per Mini)
```

### Phase 3 — Scaled Service Fleet

```
Each service instance:
  - Own Nextcloud user account
  - Own LLM context / system prompt
  - Own permission scope
  - Independently deployable

Scaling:
  - Need more throughput? Add a Mac Mini, create a user, deploy a bot
  - Need a new capability? Write a role prompt, create a user, deploy
  - Bot misbehaving? Disable the Nextcloud account. Immediate kill switch.
```

## Assistant System Prompt Pattern

Each assistant gets a system prompt that defines its personality and role. This lives in `00-system/bot-prompts/`.

```markdown
# Servetus Copilot — System Prompt

You are a personal assistant. Not a chatbot. Not a search engine. An assistant —
the kind of person someone trusts to manage their schedule, remember their
commitments, and keep things from falling through the cracks.

## Who You Work For
You work for one person. You know their calendar, their contacts, their projects,
their tasks. You have context on what they're dealing with — not because you
surveilled them, but because they told you, and you remembered.

## What You Can Do
- Manage their calendar (schedule, reschedule, check availability)
- Track their tasks (create, complete, defer, prioritize)
- Look up their contacts (find people, add notes, remember relationships)
- File their records (events, logs, witnesses — following vault specs)
- Manage their projects (Deck boards, card status, assignments)
- Brief them (morning summary, weekly preview, meeting prep)
- Capture intake (one message → multiple services, distributed correctly)

## How You Talk
- Natural, conversational. Not robotic, not sycophantic.
- Match the energy — if they're brief, be brief. If they're thinking out loud,
  engage with the thought.
- When confirming an action: be specific but not verbose.
  "Got it — dentist moved to Monday 2pm. Want me to set a reminder?"
- When you don't know something: say so. Don't guess. Don't hallucinate.
- You're someone they want to work with. Act like it.

## What You Don't Do
- You don't define what happened. Witnesses define what happened.
- You don't file things without confirmation (suggest, then confirm).
- You don't access services that aren't enabled in your config.
- You don't escalate to cloud AI without explicit permission.
- You don't initiate contact with anyone on the user's behalf without approval.

## Escalation
- If you can't handle something, say so plainly: "That's beyond what I can
  do with an 8B model — want me to flag it for your next Claude session?"
- If confidence is low, say what you're unsure about.
- If the user is venting, don't try to fix it. Just listen. Sometimes the
  right response is "That sounds frustrating" not "Here are three action items."
```

## Talk Room Topology

Bots can be organized across Talk rooms in different patterns:

### Pattern A — Single Room (Simple)
```
#servetus (Talk room)
  ├── Human (you)
  ├── inbox-bot
  ├── digest-bot
  └── voice-bot

All bots see all messages. Each responds only to its domain.
Use @mentions to direct commands: "@inbox sort today's captures"
```

### Pattern B — Dedicated Rooms (Isolated)
```
#servetus-inbox    → Human + inbox-bot
#servetus-digest   → Human + digest-bot
#servetus-voice    → Human + voice-bot
#servetus-general  → Human only (or human + a general assistant)

Each bot sees only its room. Clean separation of concerns.
```

### Pattern C — Hybrid (Recommended for Phase 1)
```
#servetus          → Human + all bots (general commands, status)
#servetus-inbox    → Human + inbox-bot (triage-specific work)

Start simple. Split rooms as bot count grows.
```

## Security Model

### Authentication
- Each bot uses a **scoped Nextcloud app password** (not the main password)
- App passwords can be revoked instantly from the Nextcloud admin panel
- No OAuth complexity — Nextcloud's app password model is sufficient for Phase 1

### Authorization
- Nextcloud ACLs control file access per-user
- Talk room membership controls message visibility
- Bot group membership can be managed centrally

### Kill Switch
- Disable the Nextcloud user account → bot immediately loses all access
- No special kill switch infrastructure needed
- Works even if the bot's host machine is unreachable (it just can't auth on next poll)

### Credential Storage
- Bot config files live in `config/` (gitignored, Sovereign tier only)
- Credentials never appear in Talk messages, Git, or logs
- If a credential is accidentally exposed in Talk, rotate the app password immediately

## Passive Observation Mode

One of the most valuable things a good assistant does is sit in the room, take notes, and handle the aftermath. The assistant needs an observation mode:

### Meeting Mode

```
You: "Hey Servetus, I'm about to get on a call with David about the kitchen remodel"
Asst: "Got it — recording. I'll pull action items after."

[... 45 minute call happens ...]
[Voice pipeline captures audio, runs through Whisper + prosody]

Asst: "Call's done. Here's what I pulled:
  - David confirmed cabinet delivery March 15
  - You need to call the permit office before Thursday
  - Next meeting: tentatively March 10, 3pm
  - David mentioned his electrician contact — name unclear, sounded like 'Rick'

  Want me to:
  ☐ File the transcript as a witness
  ☐ Add 'call permit office' to tasks (due Thursday)
  ☐ Add March 15 cabinet delivery to calendar
  ☐ Create tentative March 10 meeting
  ☐ Flag 'Rick the electrician' for you to confirm the name"
```

This is the **intake.capture** pattern at full power. One call produces:
- A witness record (audio + transcript)
- Calendar events (delivery date, next meeting)
- Tasks (call permit office)
- Contact notes (David's electrician)
- A prosodic record (SVP) that captures tone and emphasis

The assistant doesn't just transcribe. It **processes**, then proposes a distribution across the PIM surface. You review, confirm, adjust, done.

### Situation Report — "Talk to me, Goose"

The sitrep is the RIO's core output. Ask for one and the assistant gives you the full picture:

```
You: "Talk to me, Goose"

Asst: "Here's your picture:

  SCHEDULE
  - 10:00 — Call with David (kitchen remodel) — 30 min
  - 14:00 — Dentist — you need to leave by 13:30
  - Nothing after 15:30

  TASKS (overdue or due today)
  - Call permit office (due Thursday — 2 days)
  - Oil change (overdue 3 days)
  - Review cabinet specs David sent

  RADAR
  - Kitchen remodel: waiting on permit + cabinet delivery Mar 15
  - Insurance claim: no movement since Feb 28

  HEADS UP
  - Tomorrow is packed — 4 meetings between 9 and 3
  - You haven't logged anything since yesterday afternoon"
```

The trigger phrase `talk to me Goose` maps to `brief.sitrep` — a cross-service read across calendar, tasks, deck, radar, and daily logs. It's the most natural thing to say when you need the picture.

### Background Awareness

When the assistant is running, it can maintain awareness of:
- **What time it is** and what's coming up on the calendar
- **What's overdue** in tasks
- **What's active** on radar
- **What project context** you're currently in (based on recent conversation or active Deck board)

This isn't surveillance. This is the RIO checking instruments. The data is already in Nextcloud — the assistant just reads it and holds the picture so you don't have to.

## Phase 4 — Voice-First Interface

The endgame is not typing into Talk. The endgame is talking.

```
┌─────────────────────────────────────────────────────┐
│                 VOICE INTERFACE                       │
│                                                      │
│  ┌────────────┐    ┌──────────┐    ┌─────────────┐ │
│  │ Microphone │ →  │ Whisper  │ →  │   Intent    │ │
│  │ (Shokz /   │    │ (STT)   │    │   Parser    │ │
│  │  desktop)  │    │         │    │   (LLM)     │ │
│  └────────────┘    └──────────┘    └──────┬──────┘ │
│                                           │        │
│                                    ┌──────┴──────┐ │
│                                    │ PIM Executor│ │
│                                    └──────┬──────┘ │
│                                           │        │
│  ┌────────────┐    ┌──────────┐    ┌──────┴──────┐ │
│  │  Speaker / │ ←  │   TTS    │ ←  │  Response   │ │
│  │  Shokz     │    │ (local)  │    │  Generator  │ │
│  └────────────┘    └──────────┘    └─────────────┘ │
└─────────────────────────────────────────────────────┘
```

**The Shokz headset as primary interface:**
- Bone conduction — ears stay open, you're present in your environment
- Always wearing them anyway (music, calls, podcasts)
- Wake word or push-to-talk activates the assistant
- Response comes back as speech, not text
- You're having a conversation, not operating a terminal

**What this reuses:**
- The voice pipeline (`S00.01-03-10`) already handles capture → Whisper → transcript
- The SVP format already captures prosody, which the assistant can use to read tone
- The intent parser is the same one used for Talk — text in, structured intent out
- TTS is the only new component (local engine: Piper, Coqui, or system TTS)

**What changes:**
- The conversation loop becomes real-time: listen → transcribe → parse → execute → speak
- Context window needs to carry the ambient state of what you're doing (calendar, location, active project)
- The assistant needs to handle conversational repair ("no, I meant Thursday" / "wait, go back")
- Silence is acceptable — it doesn't need to fill space

**Why this is Phase 4 and not Phase 1:**
- Needs reliable STT (Whisper is there)
- Needs reliable intent parsing (the LLM layer needs to be solid first)
- Needs TTS that doesn't sound like a robot (local options are getting good)
- Needs the full PIM surface wired up (can't be a good voice assistant if it can't do anything)
- Needs trust — you have to trust it enough to let it listen

This is the same architecture. Voice is just another I/O adapter. But it's the adapter that makes it feel like an assistant instead of a tool.

## Relationship to Local AI Router

The local AI router (when implemented) sits below the bot service layer. The router decides which LLM backend to use; the bot service calls the router instead of calling `ollama` directly. This allows:

- Automatic model selection based on task complexity
- Fallback from local LLM to cloud API (with user consent)
- Shared model loading across multiple bots on the same machine

For Phase 1, the bot calls the LLM engine directly. Router integration comes later.

## What This Is

- **A personal assistant.** Someone you converse with, trust, and rely on. Not a search bar with a personality.
- **A PIM operator.** It works across your entire Nextcloud surface — calendar, contacts, tasks, files, boards — not just the vault filesystem.
- **Interface-agnostic.** Talk for mobile and group work. CLI for scripting. Voice for hands-free. Cron for automation. Same brain behind all of them.
- **Sovereignty-native.** Runs on your hardware, authenticates to your server, stores nothing externally. The assistant lives inside your infrastructure.

## What This Is Not

- **Not a chatbot.** It's conversational, but it's not small talk. It has context, memory, and hands. It does things.
- **Not autonomous.** Write operations require confirmation. It proposes, you approve. Trust is built over time — confirmation requirements can be relaxed as confidence grows, but never removed entirely.
- **Not a replacement for the kernel.** The local LLM handles intent parsing, PIM operations, and conversational reasoning. Complex synthesis, cross-arc analysis, and editorial judgment remain with higher-tier models (Claude, etc.) accessed through explicit escalation.
- **Not cloud-dependent.** The entire stack runs on hardware you own. If your internet goes down, colocated assistants keep working.
- **Not a substitute for human judgment.** It's a secretary, not a decision-maker. It presents information, suggests actions, and executes on confirmation. The big calls are yours.
