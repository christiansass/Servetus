# Servetus Reporter Spec — Internal PR Newsroom

## Purpose

Reporter is the vault's internal newsroom. It captures work accomplished across
sessions, decides what is safe for public consumption, and produces publication-ready
drafts for external platforms — without ever publishing autonomously.

Reporter does not replace 09-Shared. It feeds it. 09-Shared remains the deliberate
publication threshold per the Shared Spec. Reporter is the editorial desk that
prepares material to cross that threshold.

---

## What Reporter Is

- A **session work logger** — captures what was built, fixed, decided, or shipped
- A **sanitization engine** — strips PII, sovereign-tier references, and internal
  context before any content leaves the vault
- A **multi-platform drafting system** — produces platform-specific output for
  GitHub, WordPress, self-hosted blogs, and other destinations
- An **internal PR archive** — every draft, every revision, every publish decision
  is stored in the vault as a permanent record

## What Reporter Is Not

- Not a publishing bot. Reporter drafts. Humans approve. Nothing goes out without
  explicit authorization.
- Not a social media manager. Reporter produces long-form update content — project
  news, changelogs, technical posts. Not tweets. Not engagement bait.
- Not a replacement for the disclosure spec. Reporter operates *under* the trust
  circle framework (S00.01-06-00), not alongside it.

---

## Operating Principles

### 1. The Vault Is the Source of Truth

Reporter reads from the vault — session logs, changelogs, project files, arc
updates, committed code. It does not fabricate accomplishments. Every claim in
a Reporter draft must trace to a vault artifact, commit, or session record.

### 2. Public Circle Only

All Reporter output is destined for the **public** trust circle. Reporter applies
the strictest interpretation of disclosure rules. If content would not survive
the four-layer permission chain at the public level, it does not appear in any
Reporter draft.

Content from sovereign-tier folders (`00-Artifacts/`, `02-Memories/`,
`03-Events/`, `06-Radar/`, `08-Witnesses/`) is **never referenced** in Reporter
output — not even indirectly. Reporter draws from:

- `Toolkit/` specs (public-tier acceptable per guardrails)
- `CHANGELOG.md` and `README.md` (public-tier)
- Git commit history (public repo only)
- `04-Projects/` entries **only when** `circles.read: public` or explicitly
  marked for publication
- `05-Arcs/` entries **only when** explicitly flagged `reporter: true` in
  frontmatter

### 3. Sanitization Before Drafting

Reporter sanitizes **before** composing, not after. The sanitization pass runs
first, producing a clean context window. The draft is then composed from
sanitized inputs only. This prevents accidental leakage through phrasing,
implication, or structural inference.

**Sanitization checks:**

| Check | Action |
|-------|--------|
| Person names (real) | Replace with role descriptors or omit |
| Internal project codenames | Use public-facing names only |
| Client references | Strip entirely — Rule 5 (cross-client isolation) |
| IP addresses, hostnames, paths | Generalize or omit |
| Vault internal paths | Never surface (`02-Memories/...` → not mentioned) |
| Unreleased feature details | Hold until explicitly cleared for publication |
| Financial figures | Strip unless explicitly cleared |
| PII map entries | Cross-reference `config/pii_map.json` — redact all matches |

### 4. Approval Before Publication

No Reporter draft is published without explicit human approval. The flow:

```
Session work occurs
    ↓
Reporter logs accomplishments (automatic, internal)
    ↓
Reporter produces draft(s) for target platform(s)
    ↓
Draft stored in vault (09-Shared/reporter/drafts/)
    ↓
Human reviews draft in Obsidian
    ↓
Human approves → draft moves to 09-Shared/reporter/approved/
    ↓
Publication executes (manual or via approved automation)
    ↓
Published version archived in 09-Shared/reporter/published/
```

For high-stakes publications (press releases, public statements, incident
reports), the Talk Approval Protocol (S00.01-14-00) may be invoked for
multi-party sign-off.

### 5. Platform-Specific Formatting

Reporter produces drafts tailored to each destination. One session's work may
produce multiple drafts — same substance, different format.

| Destination | Format | Typical Content |
|-------------|--------|-----------------|
| **GitHub Releases** | Markdown, tag-linked | Version notes, feature summaries, breaking changes |
| **GitHub Discussions / README** | Markdown | Project updates, architecture explanations |
| **WordPress** | HTML or Markdown (per theme) | Blog posts, news updates, tutorials |
| **Self-hosted blog** | Markdown with frontmatter | Technical deep-dives, project philosophy |
| **Nextcloud Collectives** | Markdown | Internal team updates (partner/staff circle) |

Each platform has a destination profile (see Destination Profiles below).

## Vault Storage

### Folder Structure

```
09-Shared/
  reporter/
    _reporter-template.md       ← Draft template
    session-logs/               ← Raw session work logs (internal, not published)
    drafts/                     ← Composed drafts awaiting review
    approved/                   ← Human-approved, ready to publish
    published/                  ← Archived published versions with metadata
```

**Git tracking:** `09-Shared/reporter/session-logs/` is gitignored (sovereign
tier — may contain internal references before sanitization). `drafts/`,
`approved/`, and `published/` may be tracked if their contents are confirmed
public-safe.

### Session Log Format

Session logs are the raw material. They capture what happened — not what to
publish. Reporter writes one per session when invoked.

```yaml
---

- [commit hashes and summaries from this session]

- [list with links]

- [key decisions with rationale]

```

    "approval_required": true,
    "auto_publish": false,
    "categories": ["development", "updates"],
    "default_status": "draft"
  },
  "self-hosted": {

    "output_dir": "09-Shared/reporter/published/blog/",
    "format": "markdown_with_frontmatter",
    "circle": "public",
    "approval_required": true,

All destinations default to `auto_publish: false`. Autonomous publishing requires
an explicit, separate configuration decision by the vault owner — it is never
the default and never assumed.

## Invocation

Reporter is invoked as a Claude Code skill: `/reporter`

### Subcommands

| Command | Action |
|---------|--------|
| `/reporter log` | Write a session log for the current session's work |
| `/reporter draft <destination>` | Produce a sanitized draft for a specific destination |
| `/reporter draft all` | Produce drafts for all configured destinations |
| `/reporter status` | Show pending drafts, approval state, publication history |
| `/reporter review <file>` | Display a draft for human review with sanitization annotations |
| `/reporter approve <file>` | Move an approved draft to the approved queue |
| `/reporter publish <file>` | Execute publication of an approved draft (requires prior approval) |

### Automatic Logging

When configured via hook, Reporter can automatically log session work at session
close (S00.01-10-91). This produces a session log only — never a draft or
publication. Drafting is always an explicit act.

## Sanitization Audit Trail

Every Reporter draft carries a sanitization log in its frontmatter:

```yaml
sanitization:
  pass_date: "2026-06-01T14:30:00-05:00"
  pii_map_version: "2026-05-28"
  redactions:
    - type: person_name
      original_context: "discussed with [redacted] about deployment"
      replacement: "discussed with a collaborator about deployment"
    - type: internal_path
      original_context: "filed in 02-Memories/"
      replacement: "[removed]"
  clean: true    # false if any redaction was uncertain and needs human review
```

If `clean: false`, the draft is flagged for manual review before it can be
approved. The human must resolve uncertain redactions before publication.

## Tone and Voice

Reporter output follows these voice guidelines:

- **Project updates:** Direct, technical, first-person plural ("we shipped,"
  "we fixed"). No marketing language. No hype. State what happened and why it
  matters.
- **Blog posts:** Conversational but substantive. The same voice as the README
  and Philosophy.md — plain-spoken, opinionated, grounded.
- **Release notes:** Terse. What changed, what broke, what to do about it.
- **Internal updates:** Operational. Status, blockers, next steps.

Reporter does not generate engagement-optimized content. It reports. The name
is literal.
