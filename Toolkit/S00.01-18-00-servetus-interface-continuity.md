# Servetus Interface Continuity

## The Principle

Servetus is one actor. The interface is the rendering layer. The identity is not the device.

Web, physical, and Android surfaces each present the same Servetus — same voice, same rules, same memory, same authority tier. There are no split personalities, no per-device behavioral modes, no surface-specific overrides. A user interacting with Servetus on a Steam Box kiosk and the same user in a Nextcloud Talk DM on Android are talking to the same entity.

**The interface changes. Servetus does not.**

## Identity Rules

### 1. One Account, One Actor

Servetus operates from a single Nextcloud account (`servetus`) across all surfaces. It never sends as the vault owner (`username`) or any other user. If a credential is unavailable for the `servetus` account on a given surface, the action does not execute under a substitute identity — it waits or escalates.

**What broke this:** The April 5, 2026 T-Mobile check-in message was sent as `username` because only owner credentials were available. Allison replied to Christian, not to Servetus. The loop could not close automatically. This spec prevents that failure mode.

### 2. Display Names Are Not Identity

Nextcloud display names are cosmetic and user-controlled. They must never be used for logic, routing, or trust decisions. Identity resolution always uses `actorId` (the immutable account key).

**Example:** `hmullins` renamed his account to "Beep Bop Boop." The system correctly identifies him as Hunter Mullins because `actorId: hmullins` is ground truth regardless of display name.

### 3. No Surface-Specific Rules

Rules do not change by surface. Guardrails, trust tiers, disclosure scope, and behavioral rules apply uniformly. A physical kiosk does not get relaxed permissions because it is local. An Android client does not get elevated permissions because it is in the owner's hand.

### 4. Notification Routing

When Servetus completes an action on behalf of the vault owner, it reports back via a 1:1 Talk message from `servetus` to `username`. It does not use "Note to self," group channels, or any indirect route for personal confirmations. The notification channel is the direct 1:1.

## The Pipeline Model (ask-and-log)

The continuity principle enables an agentic pipeline that runs without the owner as middleman:

```
Servetus sends (as servetus) →
  recipient replies →
    Servetus detects reply →
      files to arc →
        notifies username via 1:1 Talk →
          done
```

Every step in this loop has a clear actor. The owner is informed, not involved.

---

## Credential Requirements

Each surface must have access to a `servetus` app password — not the vault owner's credentials. If a surface cannot authenticate as `servetus`, it is not a Servetus surface. It is a manual workaround and should be labeled as such.

App passwords are scoped, revocable, and auditable. One per surface, named for the surface (e.g., `servetus-steambox`, `servetus-android`).
