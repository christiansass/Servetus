# Servetus Server Bot — Tool Access and Context Parity

## Problem

The Talk bot and the Claude Code CLI currently operate at different capability tiers. The CLI version has shell access, vault reads and writes, search, and full Obsidian integration. The Talk bot has none of that — it runs on injected context only and cannot act on the vault. They share an identity but not capabilities.

## Goal

Bring the server bot to full parity with the CLI version, and beyond. The Talk bot should be able to read and write vault files, run searches, check the hopper, update project state, and eventually trigger actions — all without requiring the user to switch to the CLI.

## Approach

Implement an MCP server running on the Nextcloud host that exposes vault tools to the Talk bot. Tool surface should include at minimum:

- File read
- File write
- Vault search
- Hopper check
- Project state query

## Context Injection

Automate loading of radar, active project files, and witness data at conversation start so Servetus isn't blind when a DM opens.

## Trust Boundary

Server-side MCP access operates under the same guardrails as the CLI — destructive operations require confirmation, sovereign-tier data stays sovereign, credential rules apply.

## Open Questions

- MCP server implementation choice
- Deployment model (systemd service on workstation? sidecar to talk-listener?)
- Tool priority order
- How context injection gets triggered automatically (session start hook equivalent for Talk)
