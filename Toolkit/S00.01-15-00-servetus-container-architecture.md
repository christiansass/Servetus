# Servetus Container Architecture

## Primary Rules

**Rule 0 — Ansible playbook required.**
Every container stack, script deployment, or infrastructure component built for Servetus
MUST have an accompanying Ansible playbook. Docker Compose runs the service;
Ansible deploys it to a machine. No exceptions. This is not optional housekeeping —
it is the deployment contract. If you build it without an Ansible playbook, it is not
deployable. Playbooks live in `10-System/ansible/`.

**Rule 1 — One container per bot.**
Each Servetus service runs in its own container — isolated, scoped, replaceable.
The same pattern Nextcloud uses for its own AI apps.

One `docker-compose.yml` brings the entire Servetus node up from scratch.
This is also the colo node installation package for new customers.

---

## Why Containers

| Concern | Container solution |
|---------|-------------------|
| Agent boundary enforcement (Rule 7) | Container isolation enforces it at the OS level, not just in code |
| Dependency conflicts | Each service has its own Python environment |
| Deployment reproducibility | `docker compose up` on any machine produces the same result |
| Security | Each container has only the file/network access it needs |
| Upgrades | Replace one container without touching others |
| Customer installation | One command, one config file, running in minutes |

## Container Definitions

### `servetus-display`
```yaml
# Virtual framebuffer — 1920x1080, always on
image: ubuntu:24.04
command: Xvfb :1 -screen 0 1920x1080x24 -ac +extension GLX +render -noreset
environment:
  - DISPLAY=:1
volumes:
  - /tmp/.X11-unix:/tmp/.X11-unix
restart: always
```

### `servetus-chromium`
```yaml
# Persistent browser — logged in as servetus
depends_on: [servetus-display]
image: ubuntu:24.04  # + chromium installed
environment:
  - DISPLAY=:1
volumes:
  - servetus-chromium-profile:/home/servetus/.config/chromium
  - /tmp/.X11-unix:/tmp/.X11-unix
  - vault:/vault:ro  # read vault for config
ports:
  - "127.0.0.1:9222:9222"  # remote debugging (local only)
restart: always
```

### `servetus-whisper`
```yaml
# GPU transcription queue
image: pytorch/pytorch:2.2.2-cuda11.8-cudnn8-runtime
volumes:
  - talk-audio:/audio:ro          # Talk/Audio folder (read only)
  - vault:/vault                  # write artifacts
  - whisper-state:/state          # queue state
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu]
restart: always
```

### `servetus-ollama`
```yaml
# Local LLM server
image: ollama/ollama
volumes:
  - ollama-models:/root/.ollama
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu]
ports:
  - "127.0.0.1:11434:11434"  # local only
restart: always
```

### `servetus-talk`
```yaml
# Talk listener — reads rooms, writes to vault
image: python:3.12-slim
volumes:
  - vault:/vault                  # read + write
  - ./config:/config:ro          # credentials
environment:
  - ENV_FILE=/config/nextcloud.env
restart: always
```

### `servetus-secretary`
```yaml
# Context assembly — reads vault only, no network
image: python:3.12-slim
volumes:
  - vault:/vault:ro              # read only
network_mode: none               # no network access at all
restart: on-failure
```

## Network Isolation

```
servetus-internal (bridge network):
  servetus-talk      ← can reach NC API (external) + ollama (internal)
  servetus-chromium  ← can reach internet (Servetus's browsing)
  servetus-whisper   ← no network needed (reads local files)
  servetus-ollama    ← internal only (port 11434, local)

servetus-secretary:
  network_mode: none ← completely air-gapped, reads vault files only
```

No container can reach another customer's data.
No container has more network access than its function requires.

## GPU Sharing

The GPU serves both Whisper and Ollama. Two approaches:

**Option A — Time-share (simple):**
Only one GPU container runs at a time. Whisper pauses while Ollama is
serving a response. Simple, no special config.

**Option B — MIG / GPU slicing (advanced):**
Not supported on GPU (Pascal architecture). Available on A100/H100.
Flag for future dedicated Servetus node with modern GPU.

Current recommendation: Option A. The 1080 Ti has 11GB VRAM — Whisper
small uses ~2GB, Ollama llama3.1:8b uses ~5GB. Can overlap if careful,
but time-sharing is safer and easier to reason about.

## Installation Package (Customer Deployment)

```bash
# On a fresh Linux machine with Docker + Nvidia container toolkit:

git clone https://github.com/username/Servetus
cd Servetus
cp config/nextcloud.env.example config/nextcloud.env
# Edit nextcloud.env with customer credentials

docker compose up -d

# Servetus is running. Takes ~5 minutes first boot (model downloads).
```

That's the colo node installation experience.

## Migration from Current systemd Setup

gpu node currently runs Servetus via systemd user services. Migration path:

1. Install Docker + Nvidia container toolkit on gpu node
2. Test `docker compose up` alongside existing systemd services
3. Validate all containers healthy
4. Stop and disable systemd services
5. Set Docker to start at boot

Estimated migration time: 2-3 hours. Zero data loss (vault is Nextcloud-synced).
