# Servetus Voice Pipeline

## Purpose

The voice pipeline captures audio from a local microphone, transcribes it locally using Whisper, generates a prosodic analysis (SVP), and creates a paired Witness asset — all without any data leaving the device.

This replaces closed-source transcription tools (Vibe Typer, WhisperSync, Otter) with a sovereignty-first alternative where every step is auditable and every artifact is yours.

## Architecture

```
Microphone
    │
    ▼
┌─────────────────────────────┐
│  1. CAPTURE                 │
│  Record audio to WAV/FLAC   │
│  Show waveform feedback      │
│  Save to 01-witnesses/audio/ │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  2. TRANSCRIBE              │
│  whisper.cpp / faster-whisper│
│  Local model, no network     │
│  Word-level timestamps       │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  3. ANALYZE                 │
│  Extract prosodic features   │
│  Pitch, energy, pace, pauses │
│  Generate SVP file           │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  4. WITNESS                 │
│  Create witness markdown     │
│  Link audio + SVP + text     │
│  File to 01-witnesses/       │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  5. SYNC (optional)         │
│  Copy to Nextcloud           │
│  Maintain folder structure   │
└─────────────────────────────┘
```

## Components

### 1. Audio Capture (`capture.py`)

**Input:** Microphone audio stream
**Output:** WAV file saved to `01-witnesses/audio/`

- Records from default system microphone
- Saves as WAV (lossless, archival quality)
- Filename: `voice_YYYYMMDD_HHmm.wav`
- Displays real-time waveform/level meter in terminal
- Hotkey start/stop (default: Ctrl+R to start, Enter to stop)
- Silence detection for auto-stop (configurable)

### 2. Transcription (`transcribe.py`)

**Input:** WAV file
**Output:** Transcript text with word-level timestamps

- Uses `faster-whisper` (CTranslate2 backend, faster than original Whisper)
- Default model: `base` (fast, good enough for English)
- Configurable: `tiny` | `base` | `small` | `medium` | `large-v3`
- Word-level timestamps enabled by default
- Language detection automatic
- Returns structured segments with timestamps and confidence

### 3. Prosodic Analysis (`prosody.py`)

**Input:** WAV file + transcript with timestamps
**Output:** SVP file

- Extracts fundamental frequency (F0/pitch) using `parselmouth` (Praat)
- Computes RMS energy per segment
- Calculates speaking rate (words per minute) per segment
- Detects pauses and classifies them (breath, deliberate, long, hesitation)
- Identifies emphasis via energy spikes on specific words
- Estimates emotional register from combined features
- Writes SVP format per [[S00.01-03-00-servetus-voice-performance-format(2026-02-22)]]

### 4. Witness Creation (`witness.py`)

**Input:** WAV path, SVP path, transcript text, metadata
**Output:** Witness markdown file in `01-witnesses/`

- Creates witness record following the witness template
- Links audio file, SVP file, and plain transcript
- Sets time envelope from audio timestamps
- Device: `desktop-mic` (configurable)
- Validity: `low` (single device, no corroboration — honest default)
- Includes plain text transcript in the body for readability

### 5. CLI Integration

```
servetus voice                    # Start recording, process on stop
servetus voice --file input.wav   # Process existing audio file
servetus voice --model large-v3   # Use larger Whisper model
servetus voice --no-prosody       # Skip SVP generation (faster)
servetus voice --list-devices     # Show available microphones
```

## Configuration

User preferences stored in `config/voice.yaml`:

```yaml
voice:
  model: base                    # Whisper model size
  language: en                   # Language hint (auto if omitted)
  sample_rate: 16000             # Recording sample rate
  device: default                # Microphone device
  silence_threshold: 0.01        # Auto-stop silence level
  silence_duration: 3.0          # Seconds of silence before auto-stop
  output_format: wav             # wav or flac
  prosody: true                  # Generate SVP files
  speaker: ""                    # Default speaker name for SVP headers
```

## Security Model

- **No network calls.** Whisper models are downloaded once and run locally.
- **No third-party services.** Every step runs on your hardware.
- **No telemetry.** No usage data, no analytics, no phone-home.
- **Audio stays local.** Files are written to your vault, synced only if you configure Nextcloud.
- **You own every artifact.** WAV, SVP, and witness files are plain files in plain folders.

## Multi-Pass Transcription Refinement

Raw Whisper is a single-pass transcription engine. It's accurate but not self-correcting.
Commercial tools like Otter use multi-pass refinement — a fast first pass gets words on
screen, then subsequent passes apply contextual correction. Servetus Voice implements
a similar approach, enhanced by prosodic analysis that commercial tools lack.

### Pass Architecture

```
Pass 1: Whisper (fast, local)
  └── Raw transcription with word-level timestamps and confidence scores
      Accuracy: ~85-95% depending on model size and audio quality

Pass 2: Prosodic Cross-Check
  └── SVP analysis flags words where acoustic profile conflicts
      with transcription confidence. A loud, emphasized, 400ms word
      that Whisper assigned 0.3 confidence is almost certainly wrong.
      Output: list of flagged segments with acoustic evidence

Pass 3: LLM Contextual Correction
  └── Flagged segments + surrounding context sent to an LLM
      (local model like Llama/Mistral, or Claude API if preferred)
      Semantic + acoustic evidence combined for correction
      "In a software discussion, 'urine coding' with low confidence
       at timestamp 4.2s is likely 'your encoding'"
      Output: corrected transcript with change log

Pass 4: Human Review (optional, targeted)
  └── Only flagged-and-corrected segments presented for review
      Instead of re-listening to the entire recording,
      review a short list of specific corrections with audio snippets
      Accept/reject each correction individually
```

### Advantage Over Commercial Multi-Pass

Commercial tools (Otter, etc.) use purely semantic correction — "does this word
make sense in context?" Servetus adds acoustic evidence from the prosodic layer —
"does this word make sense in context AND does it match the pitch, energy, duration,
and emphasis pattern of what was actually spoken?" This dual-signal approach catches
errors that semantic-only correction misses, and avoids false corrections where the
acoustic evidence confirms the original transcription was correct.

### Configuration

```yaml
voice:
  refinement:
    enabled: true
    passes: 3                     # 1=whisper only, 2=+prosodic, 3=+LLM, 4=+human
    llm_backend: local            # local | claude | openai
    local_model: "mistral-7b"     # For local LLM correction
    confidence_threshold: 0.7     # Flag segments below this confidence
    auto_accept_threshold: 0.95   # Auto-accept LLM corrections above this
```

## Personal Dictionary and Domain Adaptation

Generic transcription treats every speaker identically. Servetus Voice maintains a
personal vocabulary corpus that grows from your actual usage — your vault content,
your project names, the people you reference, your domain-specific terminology.

### Vocabulary Sources

```yaml
voice:
  vocabulary:
    # Explicit user-defined terms (highest priority)
    custom_terms:
      - "Servetus"
      - "Nextcloud"
      - "Obsidian"
      - "prosodic"
      - "SVP"

    # Auto-harvest from vault content (names, projects, technical terms)
    vault_harvest: true
    harvest_sources:
      - "01-witnesses/**/*.md"       # People mentioned in witnesses
      - "02-logbook/**/*.md"         # Project terminology
      - "frontmatter: tags"          # All tags as vocabulary hints

    # Domain dictionaries (loaded on demand, not pre-loaded)
    # The system infers relevant domains from vault content
    # rather than requiring manual selection
    domain_inference: true
```

### Speaker Identification

Multi-speaker conversations require knowing who said what. Servetus Voice builds
speaker profiles from vocal characteristics stored in the SVP layer:

- **Vocal fingerprint:** Pitch range, speaking rate, rhythm patterns, formant structure
- **Name association:** User assigns names to detected speakers; stored locally
- **Cross-session recognition:** "This voice matches 'Emily' from last Tuesday's session"
- **Search capability:** Find all segments where a specific speaker is talking

Speaker profiles are stored in `config/speakers/` as plain YAML files in your vault.
No cloud sync. No server-side voice database. The mapping between a voice and a name
exists only on your hardware.

### Privacy Implications

This capability is powerful and dangerous in equal measure. The same technology that
lets you search "what did Emily say about the API redesign last month" could be used
as a surveillance tool. Servetus's position: the speaker database lives in YOUR vault
on YOUR hardware. It never leaves. There is no "shared speaker recognition service."
If you delete a speaker profile, it's gone. This is architecturally different from
Otter storing voice fingerprints on their servers indefinitely.

## Environmental Audio Intelligence

Transcription assumes a clean voice signal. Reality includes background noise, multiple
speakers, environmental sounds, and degraded audio. Rather than pretending these don't
exist, Servetus Voice annotates them.

### Audio Quality Assessment

Every segment gets a quality classification:

```
quality: clear          # Clean voice, high confidence transcription
quality: noisy          # Background noise present, transcription may have errors
quality: overlapping    # Multiple speakers simultaneously, attribution uncertain
quality: degraded       # Poor audio (cell compression, rubber-banding, codec artifacts)
quality: unintelligible # Audio present but not usable for transcription
```

### Non-Speech Audio Events

The environmental layer detects and annotates non-speech sounds:

```
[00:04.2 - 00:04.8]  {event: door_closing}
[00:12.1 - 00:15.3]  {event: background_conversation, speakers: unknown}
[00:23.0 - 00:23.4]  {event: notification_sound}
[01:02.0 - 01:06.2]  {quality: degraded, reason: "cell_compression"}
[01:15.0 - 01:15.8]  {event: laughter, speaker: "primary"}
```

### Multi-Speaker Separation

Human auditory processing separates simultaneous speakers by frequency characteristics,
spatial positioning, and learned voice patterns. Digital approximation:

- **Frequency-based separation:** Different speakers occupy different pitch ranges;
  the system uses this to disentangle overlapping speech
- **Speaker diarization:** "Who is speaking when" — assigns each segment to a
  detected speaker, even without knowing their name
- **Confidence flagging:** When speakers overlap and separation is uncertain,
  the segment is flagged rather than guessed at
- **Honest failure:** If four seconds of audio is genuinely unusable — bad cell
  connection, everyone talking at once, loud environment — the system says so:
  `{quality: unintelligible, duration: 4.0s, reason: "overlapping_speakers+noise"}`
  You can go back and listen. Maybe you hear something the machine doesn't.
  That's what Pass 4 (human review) is for.

### SVP Integration

Environmental audio events are encoded in the SVP file alongside prosodic data:

```
# SVP environmental annotations
ENV 00:04.2  00:04.8  door_closing       confidence=0.82
ENV 00:12.1  00:15.3  background_speech  confidence=0.71  speakers=2
ENV 01:02.0  01:06.2  degraded_audio     reason=compression
SPK 00:00.0  00:11.9  speaker_01         label="Christian"
SPK 00:12.0  00:22.5  speaker_02         label="unknown"
```

This gives the LLM correction pass (Pass 3) additional context: "this segment had
background noise and two speakers — weight the transcription confidence accordingly."

## Contextual Awareness Integration (Future)

The broadest layer: voice transcription informed by your full situational context.
This moves beyond transcription into comprehension — the system doesn't just know
what you said, it knows what you're working on.

### Context Sources

| Source | What It Provides |
|--------|-----------------|
| Calendar | Who you're meeting with, meeting topic |
| Vault notes | Current project context, recent work |
| Address book | Expected names, correct spellings |
| Recent witnesses | Conversation continuity, topic threading |
| Tags/categories | Domain context for vocabulary biasing |

### How Context Improves Transcription

- **Name correction:** Calendar says you're meeting with "Rajesh" — when Whisper
  transcribes "Roger" with low confidence, the LLM pass knows to check
- **Topic priming:** Your recent logbook entries are about Kubernetes — bias
  toward technical vocabulary before transcription even starts
- **Continuity:** Yesterday's witness mentioned "the SVP format redesign" —
  today's conversation referencing "the format" can be linked

### Architecture Note

This layer requires MCP integration — the voice pipeline queries the vault through
the MCP server for contextual information. It does NOT require internet access.
Your calendar, contacts, and notes are all local vault data. The "prefrontal cortex"
is your vault; the MCP server is the interface.

This is an entirely new topic area that warrants its own specification document.

## Future: MCP Server

The voice pipeline will be exposed as an MCP (Model Context Protocol) server, allowing any LLM client to:
- Request a voice capture session
- Retrieve transcripts with prosodic annotations
- Search voice witnesses by content or date
- Access SVP data for context-aware responses

This is the path toward Servetus as a local runtime, not just a vault spec.
