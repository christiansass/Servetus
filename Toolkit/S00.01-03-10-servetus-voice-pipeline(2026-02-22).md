# Servetus Voice Pipeline

## Purpose

The voice pipeline captures audio from a local microphone, transcribes it locally using Whisper, generates a prosodic analysis (SVP), and creates a paired Witness asset — all without any data leaving the device.

This replaces closed-source transcription tools (Vibe Typer, WhisperSync, Otter) with a sovereignty-first alternative where every step is auditable and every artifact is yours.

## Architecture

```
Microphone
    │
    ▼
┌─────────────────────────────┐
│  1. CAPTURE                 │
│  Record audio to WAV/FLAC   │
│  Show waveform feedback      │
│  Save to 01-witnesses/audio/ │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  2. TRANSCRIBE              │
│  whisper.cpp / faster-whisper│
│  Local model, no network     │
│  Word-level timestamps       │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  3. ANALYZE                 │
│  Extract prosodic features   │
│  Pitch, energy, pace, pauses │
│  Generate SVP file           │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  4. WITNESS                 │
│  Create witness markdown     │
│  Link audio + SVP + text     │
│  File to 01-witnesses/       │

           │

└─────────────────────────────┘
```

## Components

### 1. Audio Capture (`capture.py`)

**Input:** Microphone audio stream
**Output:** WAV file saved to `01-witnesses/audio/`

- Records from default system microphone
- Saves as WAV (lossless, archival quality)
- Filename: `voice_YYYYMMDD_HHmm.wav`
- Displays real-time waveform/level meter in terminal
- Hotkey start/stop (default: Ctrl+R to start, Enter to stop)
- Silence detection for auto-stop (configurable)

### 2. Transcription (`transcribe.py`)

**Input:** WAV file
**Output:** Transcript text with word-level timestamps

- Uses `faster-whisper` (CTranslate2 backend, faster than original Whisper)
- Default model: `base` (fast, good enough for English)
- Configurable: `tiny` | `base` | `small` | `medium` | `large-v3`
- Word-level timestamps enabled by default
- Language detection automatic
- Returns structured segments with timestamps and confidence

### 3. Prosodic Analysis (`prosody.py`)

**Input:** WAV file + transcript with timestamps
**Output:** SVP file

- Extracts fundamental frequency (F0/pitch) using `parselmouth` (Praat)
- Computes RMS energy per segment
- Calculates speaking rate (words per minute) per segment
- Detects pauses and classifies them (breath, deliberate, long, hesitation)
- Identifies emphasis via energy spikes on specific words
- Estimates emotional register from combined features
- Writes SVP format per [[S00.01-03-00-servetus-voice-performance-format(2026-02-22)]]

### 4. Witness Creation (`witness.py`)

**Input:** WAV path, SVP path, transcript text, metadata
**Output:** Witness markdown file in `01-witnesses/`

- Creates witness record following the witness template
- Links audio file, SVP file, and plain transcript
- Sets time envelope from audio timestamps
- Device: `desktop-mic` (configurable)
- Validity: `low` (single device, no corroboration — honest default)
- Includes plain text transcript in the body for readability

### 5. CLI Integration

```
servetus voice                    # Start recording, process on stop
servetus voice --file input.wav   # Process existing audio file
servetus voice --model large-v3   # Use larger Whisper model
servetus voice --no-prosody       # Skip SVP generation (faster)
servetus voice --list-devices     # Show available microphones
```

## Security Model

- **No network calls.** Whisper models are downloaded once and run locally.
- **No third-party services.** Every step runs on your hardware.
- **No telemetry.** No usage data, no analytics, no phone-home.
- **Audio stays local.** Files are written to your vault, synced only if you configure Nextcloud.
- **You own every artifact.** WAV, SVP, and witness files are plain files in plain folders.

## Multi-Pass Transcription Refinement

Raw Whisper is a single-pass transcription engine. It's accurate but not self-correcting.
Commercial tools like Otter use multi-pass refinement — a fast first pass gets words on
screen, then subsequent passes apply contextual correction. Servetus Voice implements
a similar approach, enhanced by prosodic analysis that commercial tools lack.

### Pass Architecture

```
Pass 1: Whisper (fast, local)
  └── Raw transcription with word-level timestamps and confidence scores
      Accuracy: ~85-95% depending on model size and audio quality

Pass 2: Prosodic Cross-Check
  └── SVP analysis flags words where acoustic profile conflicts
      with transcription confidence. A loud, emphasized, 400ms word
      that Whisper assigned 0.3 confidence is almost certainly wrong.
      Output: list of flagged segments with acoustic evidence

Pass 3: LLM Contextual Correction
  └── Flagged segments + surrounding context sent to an LLM
      (local model like Llama/Mistral, or Claude API if preferred)
      Semantic + acoustic evidence combined for correction
      "In a software discussion, 'urine coding' with low confidence
       at timestamp 4.2s is likely 'your encoding'"
      Output: corrected transcript with change log

Pass 4: Human Review (optional, targeted)
  └── Only flagged-and-corrected segments presented for review
      Instead of re-listening to the entire recording,
      review a short list of specific corrections with audio snippets
      Accept/reject each correction individually
```

### Advantage Over Commercial Multi-Pass

Commercial tools (Otter, etc.) use purely semantic correction — "does this word
make sense in context?" Servetus adds acoustic evidence from the prosodic layer —
"does this word make sense in context AND does it match the pitch, energy, duration,
and emphasis pattern of what was actually spoken?" This dual-signal approach catches
errors that semantic-only correction misses, and avoids false corrections where the
acoustic evidence confirms the original transcription was correct.

### Configuration

```yaml
voice:
  refinement:
    enabled: true
    passes: 3                     # 1=whisper only, 2=+prosodic, 3=+LLM, 4=+human
    llm_backend: local            # local | claude | openai
    local_model: "mistral-7b"     # For local LLM correction
    confidence_threshold: 0.7     # Flag segments below this confidence
    auto_accept_threshold: 0.95   # Auto-accept LLM corrections above this
```

### Speaker Identification

Multi-speaker conversations require knowing who said what. Servetus Voice builds
speaker profiles from vocal characteristics stored in the SVP layer:

- **Vocal fingerprint:** Pitch range, speaking rate, rhythm patterns, formant structure
- **Name association:** User assigns names to detected speakers; stored locally
- **Cross-session recognition:** "This voice matches 'Emily' from last Tuesday's session"
- **Search capability:** Find all segments where a specific speaker is talking

Speaker profiles are stored in `config/speakers/` as plain YAML files in your vault.
No cloud sync. No server-side voice database. The mapping between a voice and a name
exists only on your hardware.

### Privacy Implications

This capability is powerful and dangerous in equal measure. The same technology that
lets you search "what did Emily say about the API redesign last month" could be used
as a surveillance tool. Servetus's position: the speaker database lives in YOUR vault
on YOUR hardware. It never leaves. There is no "shared speaker recognition service."
If you delete a speaker profile, it's gone. This is architecturally different from
Otter storing voice fingerprints on their servers indefinitely.

## Environmental Audio Intelligence

Transcription assumes a clean voice signal. Reality includes background noise, multiple
speakers, environmental sounds, and degraded audio. Rather than pretending these don't
exist, Servetus Voice annotates them.

### Audio Quality Assessment

Every segment gets a quality classification:

```
quality: clear          # Clean voice, high confidence transcription
quality: noisy          # Background noise present, transcription may have errors
quality: overlapping    # Multiple speakers simultaneously, attribution uncertain
quality: degraded       # Poor audio (cell compression, rubber-banding, codec artifacts)
quality: unintelligible # Audio present but not usable for transcription
```

### Non-Speech Audio Events

The environmental layer detects and annotates non-speech sounds:

```
[00:04.2 - 00:04.8]  {event: door_closing}
[00:12.1 - 00:15.3]  {event: background_conversation, speakers: unknown}
[00:23.0 - 00:23.4]  {event: notification_sound}
[01:02.0 - 01:06.2]  {quality: degraded, reason: "cell_compression"}
[01:15.0 - 01:15.8]  {event: laughter, speaker: "primary"}
```

### Spatial Audio and Multi-Microphone Awareness

Transcription tools typically treat audio as a flat mono signal, discarding all spatial
information. Human hearing uses two sensors (ears) with known geometry to extract rich
spatial data. Digital devices can do the same — if we use what the hardware provides.

#### What Two Microphones Give You

The minimum viable spatial unit is two microphones. With just two, you get:

- **Interaural Time Difference (ITD):** Sound reaches each mic at slightly different
  times. Even microseconds of delay encodes direction. A voice to your left arrives
  at the left mic first.
- **Interaural Level Difference (ILD):** The closer mic receives a louder signal.
  High frequencies attenuate faster with distance, so ILD is especially informative
  above ~1500Hz.
- **Proximity detection via frequency profile:** A speaker 2 feet away produces strong
  high-frequency content (sibilants: "s", "f", "sh"). A voice through a wall or
  across the room loses those highs and retains only lows. Two mics + frequency
  analysis = distance estimation.
- **Near-field vs. far-field classification:** The primary speaker (close to device)
  has a fundamentally different spectral signature than background speakers.

#### Sub-Audible and Tactile Frequencies

Below ~80Hz, humans perceive vibration through bone conduction and body resonance
more than through the eardrum. This is real sensory data — you feel the bass, you
don't hear it. While most device microphones roll off below 100Hz, the principle
matters: low-frequency content in a recording (room rumble, HVAC, traffic) carries
environmental information even if it's not "speech."

#### Hardware Reality: Apple vs. Android

| Device | Microphones | Geometry Known | Beamforming |
|--------|------------|----------------|-------------|
| iPhone 14+ | 4-6 mics | Yes, fixed | Yes, hardware-level |
| iPad Pro | 5 mics | Yes, fixed | Yes |
| MacBook | 3 mics | Yes, fixed | Yes |
| Android flagship | 2-3 mics | Varies by model | Sometimes |
| Android budget | 1-2 mics | Unknown | No |
| USB podcast mic | 1 (usually) | N/A | No |
| Stereo recorder | 2, known spacing | Yes | Manual |

**The Android problem:** Apple controls the hardware, so mic positions are known and
consistent. A beamforming algorithm for iPhone 15 works on every iPhone 15. Android
spans thousands of hardware configurations. A Samsung Galaxy S24 has different mic
placement than a Pixel 8 than a OnePlus 12.

**Minimum hardware floor for spatial features:**

```yaml
voice:
  spatial:
    enabled: auto                    # auto-detect mic count
    min_microphones: 2               # Spatial features require >= 2 mics
    mic_geometry: auto               # Known devices have preset geometry
    fallback: mono                   # Single mic: spatial features disabled,
                                     # frequency-only separation still active
```

When spatial features are unavailable (single mic), the system falls back to
frequency-only speaker separation — pitch range, formant structure, speaking rate.
Less accurate than spatial+frequency, but still better than nothing.

#### Beamforming for Speaker Isolation

With known microphone geometry and >= 2 mics, beamforming focuses the "listening
direction" toward the primary speaker and attenuates other directions:

```
Mic 1 (bottom) ─┐
                 ├── Beamforming ──> Primary speaker signal (enhanced)
Mic 2 (top)    ─┘                   Background signal (attenuated)
                                    Spatial metadata (direction estimates)
```

This directly feeds speaker diarization: "the voice coming from 30° left is Speaker A,
the voice from directly ahead is Speaker B."

### Multi-Speaker Separation

Human auditory processing separates simultaneous speakers by frequency characteristics,
spatial positioning, and learned voice patterns. Digital approximation uses both
spatial and spectral cues when available:

- **Spatial separation (multi-mic):** Direction-of-arrival estimation isolates speakers
  by physical location. Most reliable method when hardware supports it.
- **Frequency-based separation:** Different speakers occupy different pitch ranges;
  the system uses this to disentangle overlapping speech. Works with single mic.
- **Proximity classification:** Near-field speaker (strong high frequencies, direct
  signal) vs. far-field speaker (attenuated highs, more reverb). A voice through
  a wall has a distinctly different spectral envelope than one in the room.
- **Speaker diarization:** "Who is speaking when" — assigns each segment to a
  detected speaker, even without knowing their name. Uses spatial+spectral+temporal
  cues combined.
- **Confidence flagging:** When speakers overlap and separation is uncertain,
  the segment is flagged rather than guessed at.
- **Honest failure:** If four seconds of audio is genuinely unusable — bad cell
  connection, everyone talking at once, loud environment — the system says so:
  `{quality: unintelligible, duration: 4.0s, reason: "overlapping_speakers+noise"}`
  You can go back and listen. Maybe you hear something the machine doesn't.
  That's what Pass 4 (human review) is for.

### SVP Integration

Environmental and spatial audio events are encoded in the SVP file alongside
prosodic data:

```
# SVP environmental annotations
ENV 00:04.2  00:04.8  door_closing       confidence=0.82
ENV 00:12.1  00:15.3  background_speech  confidence=0.71  speakers=2
ENV 01:02.0  01:06.2  degraded_audio     reason=compression

# SVP speaker annotations with spatial data
SPK 00:00.0  00:11.9  speaker_01  label="Christian"  proximity=near  direction=0°
SPK 00:12.0  00:22.5  speaker_02  label="unknown"    proximity=far   direction=140°
SPK 00:22.6  00:25.0  speaker_01  label="Christian"  proximity=near  direction=0°

# Spatial metadata (when multi-mic available)
MIC channels=2  geometry=iphone15_default  sample_rate=48000
```

This gives the LLM correction pass (Pass 3) additional context: "this segment had
background noise and two speakers — weight the transcription confidence accordingly."

## Multi-Witness Corroboration

A single recording is a claim. Multiple independent recordings of the same event,
time-synced and cross-referenced, are evidence. This is the principle behind
courtroom testimony, investigative journalism, and aviation black boxes — and it
is the architectural foundation of Servetus witnesses.

The existing witness template already tracks `device_count` and `artifact_count`
as validity metrics. This section formalizes the multi-witness corroboration system:
how multiple independent recordings are synchronized, cross-referenced, and validated
against each other.

### The Corroboration Model

```
EVENT: "Meeting with Emily, 2026-02-22 14:30 CST"
  │
  ├── Witness A: Your phone (iPhone, pocket, 4 mics)
  │   ├── audio/witness_a_20260222_1430.wav
  │   ├── svp/witness_a_20260222_1430.svp
  │   └── 2026-02-22--meeting-emily--witness-a.md
  │
  ├── Witness B: Laptop on table (MacBook, 3 mics, closer to Emily)
  │   ├── audio/witness_b_20260222_1430.wav
  │   ├── svp/witness_b_20260222_1430.svp
  │   └── 2026-02-22--meeting-emily--witness-b.md
  │
  ├── Witness C: Conference room camera (video + audio)
  │   ├── video/witness_c_20260222_1430.mp4
  │   ├── svp/witness_c_20260222_1430.svp
  │   └── 2026-02-22--meeting-emily--witness-c.md
  │
  └── CORROBORATION RECORD
      └── 2026-02-22--meeting-emily--corroboration.md
```

Each witness is independent — it was captured by a different device, from a different
physical position, with its own microphone characteristics and spatial perspective.
The corroboration record is a derived document that cross-references all witnesses.

### Time Synchronization

Multi-witness corroboration requires all sources to share a common timeline.
Without timecode sync, you can't cross-reference "what Device A heard at 14:32.4"
with "what Device B heard at 14:32.4."

#### Sync Methods (in order of precision)

| Method | Precision | Requirements |
|--------|-----------|-------------|
| NTP network time | ~10-50ms | All devices on network, NTP client |
| GPS time | ~1ms | GPS receiver or phone with GPS |
| Acoustic sync pulse | ~0.1ms | One device emits a reference tone at start |
| Shared audio event | ~50-200ms | Post-hoc alignment using a common sound (clap, door) |
| Manual alignment | ~500ms+ | Human aligns waveforms visually in editor |

**Recommended approach:** NTP time as baseline (every phone and laptop has it),
with an acoustic sync pulse for sub-millisecond alignment when precision matters.
The acoustic pulse is simple: one device plays a short reference tone at session
start; all other devices record it; alignment is automatic in post-processing.

```yaml
voice:
  corroboration:
    sync_method: ntp              # ntp | gps | acoustic_pulse | manual
    sync_tolerance_ms: 50         # Maximum acceptable drift between sources
    reference_device: ""          # Which device is the timecode master
    acoustic_pulse:
      frequency: 1000             # Hz — easily detected, won't be confused with speech
      duration_ms: 200            # Short enough to not interfere
      pattern: "pip-pip-pip"      # Three pulses for unambiguous detection
```

### Cross-Reference Validation

Once witnesses are time-synced, the corroboration engine compares them:

#### Transcript Agreement

For each transcribed segment, compare across all witnesses:

```
Timestamp 14:32.4 — "We agreed to fifty thousand"
  Witness A: "We agreed to fifty thousand"    confidence: 0.92  quality: clear
  Witness B: "We agreed to fifteen thousand"  confidence: 0.61  quality: noisy
  Witness C: "We agreed to fifty thousand"    confidence: 0.88  quality: clear

  CORROBORATION: 2/3 agree, "fifty thousand"
  Witness B flagged: low confidence + noisy quality explains disagreement
  RESULT: CORROBORATED (high confidence)
```

#### Disagreement Classification

When witnesses disagree, the system classifies why:

| Disagreement Type | Meaning | Action |
|-------------------|---------|--------|
| Quality-explained | One source was noisy/degraded | Trust the clearer sources |
| Confidence-explained | One source had low Whisper confidence | Trust higher confidence |
| Genuine ambiguity | Multiple sources disagree with similar confidence | Flag for human review |
| Contradictory | Clear sources disagree on substance | Critical flag — something is wrong |

The last case — clear recordings that contradict each other — is the most
interesting. It almost never happens with honest recordings. When it does,
it's either a processing error or evidence of tampering.

#### Speaker Attribution Validation

Different devices hear different speakers with different clarity:

```
Timestamp 14:32.4
  Witness A (your pocket): Speaker="Christian" confidence=0.95, proximity=near
  Witness B (on table):    Speaker="Emily"     confidence=0.90, proximity=near
  Witness C (room camera): Speaker="Emily"     confidence=0.82, proximity=far

  Cross-reference: Witnesses B and C agree on speaker, A is closest to you
  and may have picked up your sub-vocalization. Flag for review.
```

#### Audio Fingerprint Matching

Beyond transcript comparison, raw audio can be cross-referenced:

- **Waveform correlation:** The same sound event should appear in all recordings
  at the synced timestamp (with level/frequency differences due to position)
- **Environmental consistency:** All devices should capture the same background
  sounds (HVAC, traffic, door closing) — if one device doesn't, why?
- **Temporal consistency:** No gaps in one recording that other recordings cover
  without interruption (detects selective editing or recording manipulation)

### Integrity and Chain of Custody

Multi-witness corroboration is only meaningful if the recordings are trustworthy.
The system supports integrity verification:

- **Recording hashes:** SHA-256 hash of each WAV/video file computed at capture time,
  stored in the witness frontmatter. Any modification to the file changes the hash.
- **Timestamp attestation:** Device clock offset from NTP recorded at session start
  and end. Proves the timestamps weren't manipulated after the fact.
- **Continuous recording verification:** Audio energy analysis confirms no silent
  gaps that would indicate stop/start editing. A genuine recording has continuous
  background noise; a spliced recording has detectable discontinuities.
- **Cross-device consistency:** If all three devices recorded the same door closing
  at 14:35.2, and one device's copy of that event has been shifted or removed,
  the inconsistency is detectable.

```yaml
# Per-witness integrity metadata
integrity:
  file_hash: "sha256:a1b2c3d4..."
  hash_computed_at: 2026-02-22T15:16:02-06:00
  ntp_offset_start_ms: 3
  ntp_offset_end_ms: 7
  continuous_recording: true
  background_noise_consistent: true
```

### Why This Matters

This is not paranoia engineering. This is what makes the difference between
"I recorded a meeting" and "I have verifiable evidence of what was said in a meeting."

- **Legal:** Multi-source corroborated recordings with integrity hashes and
  chain-of-custody documentation are substantially more credible than a single
  phone recording that could have been edited.
- **Personal:** When you're trying to remember what was actually agreed upon
  three months ago, a corroborated transcript with a 0.96 agreement score
  is more trustworthy than your memory or a single recording.
- **Philosophical:** This is the Servetus epistemology in practice —
  reality happened, witnesses captured it independently, cross-reference
  confirms the record. Truth isn't claimed; it's demonstrated through
  convergent evidence.

### How Context Improves Transcription

- **Name correction:** Calendar says you're meeting with "Rajesh" — when Whisper
  transcribes "Roger" with low confidence, the LLM pass knows to check
- **Topic priming:** Your recent logbook entries are about Kubernetes — bias
  toward technical vocabulary before transcription even starts
- **Continuity:** Yesterday's witness mentioned "the SVP format redesign" —
  today's conversation referencing "the format" can be linked

### Architecture Note

This layer requires MCP integration — the voice pipeline queries the vault through
the MCP server for contextual information. It does NOT require internet access.
Your calendar, contacts, and notes are all local vault data. The "prefrontal cortex"
is your vault; the MCP server is the interface.

This is an entirely new topic area that warrants its own specification document.

## Future: MCP Server

The voice pipeline will be exposed as an MCP (Model Context Protocol) server, allowing any LLM client to:
- Request a voice capture session
- Retrieve transcripts with prosodic annotations
- Search voice witnesses by content or date
- Access SVP data for context-aware responses

This is the path toward Servetus as a local runtime, not just a vault spec.
