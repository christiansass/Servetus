# Servetus Emergency Succession Protocol (ESP)

**Status: STUB — design decided 2026-04-12, implementation queued.**

Full design decisions in: `02-Memories/2026-04-12-emergency-succession-protocol.md`

---

## Purpose

The vault is the owner's operational brain. If the owner is incapacitated, work
must continue. ESP provides pre-authorized, scope-limited, fully audited continuity
access — without requiring the owner to be present to grant it.

Distinct from delegation: delegation is a conscious pre-act by the owner.
ESP fires when the owner cannot act.

---

## Succession Chain

Defined in witness file frontmatter (`succession` block). Queried at ESP activation.

```yaml
  role: primary       # primary | secondary
  order: 1            # sort order within role tier
```

## Activation

### Trigger conditions (ALL must be true)
1. Owner has had no vault session in ≥ N days (default: 7, configurable)
2. Designated holder explicitly runs `servetus esp activate`
3. System confirms threshold is met
4. Optional quorum: for secondary succession, 2-of-N keyring members must confirm

### Activation command (not yet built)
```bash
servetus esp activate
# → checks inactivity threshold
# → prompts for confirmation ("You are activating emergency succession as jcoler")
# → issues ESP token with 30-day expiry
```

## Session Behavior Under ESP

- Launch brief shows prominent warning banner: `⚠ ESP MODE — jcoler operating username vault`
- `SERVETUS_MODE=esp` set in environment
- `SERVETUS_USER=jcoler` (operator identity preserved — never masked)

### Artifacts
```yaml
session-mode: esp
session-user: jcoler         # who is operating
esp-delegator: username         # whose vault
esp-activated: "2026-04-12T..."
esp-expires: "2026-05-12T..."
```

---

## Scope Limits

### Allowed under continuity scope
- Read full vault within normal trust-tier access
- Continue active arcs and projects
- Respond operationally on behalf of owner
- Relay communications
- Reference non-intimate memories (self/intimate circles remain locked)

### Not allowed regardless of scope
- Grant or revoke CLI access
- Modify succession order or designations
- Access self/intimate circle records
- Represent as owner in external legal or financial commitments
- Make irreversible decisions

---

## Handback

Owner logs in once → ESP token automatically invalidated. No ceremony required.
All ESP artifacts remain permanently marked — they are part of the record.

---

## Revocation (before expiry)
- Owner: logs in (automatic)
- Holder: `servetus esp release` (voluntary)
- Hard expiry: 30 days from activation (renewable by holder only)

---

## Secondary Succession

If primary holder (collaborator-a) is also unavailable:
- Requires 2-of-N quorum from active keyring members
- Scope narrows to read-only + communication relay
- No operational decisions permitted
- 7-day maximum before requiring re-confirmation
