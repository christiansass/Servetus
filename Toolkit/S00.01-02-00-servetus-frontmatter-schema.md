# Servetus Frontmatter Schema v2

## Design Principles

**Flat, not nested.** Obsidian's Properties panel and Dataview queries both work better with flat key-value pairs. Nested objects (`servitus:`, `identity:`, `time:` as parent keys) render as opaque objects in Obsidian and are harder to query. Version 2 flattens everything to the top level.

**Prefixed to avoid collisions.** All Servetus keys use the `sv_` prefix. This prevents collisions with Obsidian's reserved keys (`tags`, `aliases`, `cssclass`) and third-party plugin keys.

**No dead fields.** Only include fields that are actually used. Do not add fields speculatively.

---

## Schema v2 — Flat Structure

```yaml
---
# ── Core identity ──────────────────────────────────────────────────────────────
sv_schema: 2
sv_version: "0.3.5"
sv_id: "SV-YYYYMMDD-CST-XXXX"
sv_slug: "kebab-case-title"
title: "Human Readable Title"

# ── Classification ─────────────────────────────────────────────────────────────
sv_type: <arc|event|memory|record|project|spec|daily_log|witness|artifact_stub>
sv_stage: <inbox|distilled|canon|published|archive>
sv_status: <draft|active|parked|final>
sv_intent: <capture|synthesis|reference|decision|plan|template>

# ── Time ───────────────────────────────────────────────────────────────────────
sv_created: "YYYY-MM-DD"
sv_timezone: "America/Chicago"

# ── Provenance (for records and artifact stubs) ────────────────────────────────
sv_source_artifact: "[[00-Artifacts/path/to/artifact]]"   # wikilink to source
sv_nextcloud_path: "/path/from/nextcloud/root"            # for artifact stubs
sv_recorded_at: "YYYY-MM-DDTHH:MM:SS-06:00"              # original capture time, not ingest

# ── Discovery ──────────────────────────────────────────────────────────────────
tags: [tag1, tag2, tag3]
aliases: []
---
```

---

## Valid `sv_type` Values

| Value | Folder | Description |
|-------|--------|-------------|
| `arc` | `05-Arcs/` | Long-running narrative thread |
| `event` | `03-Events/` | Discrete moment in time |
| `memory` | `02-Memories/` | Single atomic idea |
| `record` | `01-Records/` | Topic-segmented extract from an artifact |
| `project` | `04-Projects/` | Work cluster with deliverables |
| `spec` | `Toolkit/` | Governing specification |
| `daily_log` | `01-Records/` | Servetus session log |
| `witness` | `08-Witnesses/` | Person or evidence file |
| `artifact_stub` | `00-Artifacts/` | Reference pointer to a file living in Nextcloud |

**Removed:** `thread_export` — this was not a content type, it described origin. Origin belongs in `sv_source_artifact`, not in `sv_type`. Existing files labeled `thread_export` are records; reclassify by content.

## Artifact Stub Pattern

When a file lives in Nextcloud (photo, video, audio, document) and should not be copied into the vault, create an artifact stub in `00-Artifacts/`:

```yaml
---
sv_schema: 2
sv_version: "0.3.5"
sv_id: "SV-20260401-CST-IMG0054"
sv_slug: "tmobile-wifi-network-list-2026-04-01"
title: "T-Mobile Wi-Fi Network List — 2026-04-01"

sv_type: artifact_stub
sv_stage: canon
sv_status: active
sv_intent: capture

sv_created: "2026-04-01"
sv_recorded_at: "2026-04-01T09:54:00-05:00"
sv_timezone: "America/Chicago"
sv_nextcloud_path: "/Photos/2026/04/01/IMG_0054-wifi-network-list.PNG"

tags: [witness, t-mobile, wifi, evidence]
---

# T-Mobile Wi-Fi Network List — 2026-04-01

File lives at `sv_nextcloud_path`. Do not copy into vault.

## Metadata
- Device: iPhone
- Location: Across from United Wireless, 3400 Broadway, Quincy IL
- EXIF timestamp: 2026-04-01T09:54:00-05:00

## Connected Records
- [[01-Records/2026/04-Apr/2026-04-01-tmobile-wifi-witness_record]]
```

## Record Pattern (topic-segmented, points to artifact)

One artifact can produce multiple records — one per topic discussed.

```yaml
---
sv_schema: 2
sv_id: "SV-20260408-CST-REC1"
sv_slug: "github-scrub-2026-04-08"
title: "GitHub History Scrub — 2026-04-08"

sv_type: record
sv_stage: distilled
sv_status: active
sv_intent: capture

sv_created: "2026-04-08"
sv_source_artifact: "[[00-Artifacts/2026/04-Apr/08/claude/2026-04-08-claude-session]]"

tags: [servetus-development, git, security, gitignore]
---
```

## Migration from v1

v1 used nested YAML (`servitus:`, `identity:`, `time:` blocks). v2 is flat with `sv_` prefix.

| v1 Key | v2 Key |
|--------|--------|
| `servitus.record_type` | `sv_type` |
| `servitus.pipeline_stage` | `sv_stage` |
| `servitus.status` | `sv_status` |
| `servitus.schema_version` | `sv_schema` |
| `servitus.system_version` | `sv_version` |
| `identity.title` | `title` |
| `identity.slug` | `sv_slug` |
| `identity.record_id` | `sv_id` |
| `time.created_at` | `sv_created` |
| `time.timezone` | `sv_timezone` |
| `keywords` | (absorbed into `tags`) |

**Migration is not retroactive.** Existing v1 files are valid. New files use v2. When editing a v1 file, migrate its frontmatter to v2 at that time.
