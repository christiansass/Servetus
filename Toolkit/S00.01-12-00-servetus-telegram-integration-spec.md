# Servetus Telegram Integration — Architecture Spec

## Purpose

This spec documents the architecture decisions for integrating Telegram as a notification surface within the Servetus ecosystem. Telegram is not a primary interaction surface. It is a tap-on-shoulder mechanism that routes the user to NC Talk, where context-aware interaction occurs.

---

## Security Model

### Bot API vs. MTProto — The Hard Limit

Telegram's **Bot API** is a simplified HTTP wrapper over MTProto. Bots created through BotFather operate under strict platform constraints:

- Bots **cannot participate in Secret Chats** — this is a hard platform limit, not a configuration option
- Bots cannot initiate conversations; they respond to user messages only
- Bot tokens are tied to a named bot identity registered with Telegram

**MTProto user accounts** (full Telegram accounts operated via library) have different capabilities:

- Can initiate and receive Secret Chats
- Operate as a full Telegram "person," not a bot
- Not subject to Bot API restrictions
- Managed via Telethon (Python library) or similar MTProto client

The Servetus integration uses **Telethon + full MTProto user accounts** for the standard and sovereign tiers, and **Bot API only** for minimum-tier deployments.

### App-Layer Encryption Option

For environments requiring confidentiality beyond what Telegram's transport provides, payload encryption is available at the application layer:

- Encrypt the message content before sending via Telethon
- Telegram sees ciphertext; message is meaningless without the key
- Key management is out-of-scope for this spec and must be handled at deployment level
- This option is independent of Secret Chat capability

### Bot Identity Policy

Any bot identity used in a Servetus deployment must follow this policy:

- **Random anonymous string** — no brand name, no product name, no identifying information in the bot username or display name
- No connection to Servetus, Binary Ranch, or any organization name should be inferrable from the bot identity
- Bot identities are disposable; rotate if exposure is suspected

### Interaction Model

Telegram's role in this architecture is **notification-only**:

- Servetus sends a tap-on-shoulder message via Telegram
- Message contains minimal content — a signal, not a payload
- User is redirected to NC Talk for actual interaction
- No vault access, no context queries, no assistant interaction occurs via Telegram

## The Sovereign Identity Stack

Each sovereign-tier installation operates a full independent identity:

| Layer | Component | Notes |
|-------|-----------|-------|
| Device | GrapheneOS | Hardened Android; no Google Play Services |
| SIM | US prepaid SIM | Cash purchase, no registration required |
| SIM role | One-time SMS receipt | Receives Telegram registration SMS, then inert |
| Network | Tailscale VPN | All Telegram traffic routes through Tailscale; location opaque to Telegram |
| Library | Telethon (Python) | Runs as systemd user service on server node |
| Session | config/telegram.session | Gitignored; never committed |
| Identity | Phone number | Authentication key only — not a persistent identifier in operational context |

The SIM's only meaningful function is to receive a single SMS at account registration time. After that, the SIM remains in the device but carries no traffic. Telegram does not require ongoing SIM activity to maintain account access once session files are established.

The phone number is an authentication artifact, not an operational identifier. No system component references it after initial registration.

---

## Multi-Tenant Model

Each Servetus installation — whether self-hosted or provisioned by Binary Ranch — receives its own isolated Telegram identity. These are not shared resources.

**Per-installation provisioning:**

- Its own SIM and phone number
- Its own Telegram "person" account (full MTProto user, not a bot)
- Its own random anonymous Telegram username
- Its own Telethon session file stored locally
- Oversight maintained by org admin holding secondary login access
- Provisioned as part of the Binary Ranch onboarding kit

This model ensures that compromise of one installation has no lateral effect on any other installation. There is no shared credential, no shared session, no shared identity surface.

## US Legal Advantage

The sovereign tier is structurally dependent on US regulatory conditions. These are current facts, not permanent guarantees.

**US prepaid SIM registration:**
- US law does not require prepaid SIM registration with government ID
- A prepaid SIM purchased with cash in the US is a clean anonymous authentication artifact
- This contrasts with: EU (Germany, France, others require ID), UK (mandatory registration under Telecommunications Act), Australia (mandatory registration since 2000), India (biometric registration required), China (real-name SIM registration law)

**Implication:** The anonymous phone number that grounds the sovereign Telegram identity is legally clean under US law. The same approach would be legally problematic or impossible in most other major jurisdictions.

**International deployments** require a separate solution:

- eSIM purchased from outside the regulated jurisdiction
- Alternative authentication method not dependent on SIM
- This is an open problem; no solution is specified in this version of the spec

---

## What Telegram Is Not

This spec exists in part to constrain scope. These uses are explicitly out of scope:

- **Not a primary interaction surface.** Users do not interact with Servetus through Telegram.
- **Not a vault access point.** No Obsidian vault data is readable, writable, or queryable via Telegram.
- **Not a context-aware assistant interface.** Servetus does not answer questions, process prompts, or return structured data via Telegram.
- **Not a logging surface.** Telegram messages are not written to vault logs or treated as memory input.

The only function of Telegram in this architecture is to deliver a signal that redirects the user to NC Talk.

## Implementation Notes

### Dependencies

```bash
pip install telethon
```

### Session File

```
config/telegram.session
```

This file must be listed in `.gitignore`. It must never be committed. It is the authentication token for the Telegram account and is equivalent in sensitivity to a private key.

### Configuration Keys

Stored in `config/nextcloud.env`:

```
TELEGRAM_API_ID=
TELEGRAM_API_HASH=
TELEGRAM_SESSION=config/telegram.session
TELEGRAM_ALLOWED_USER_IDS=
```

`TELEGRAM_ALLOWED_USER_IDS` is a comma-separated list of numeric Telegram user IDs permitted to trigger Servetus behavior. Messages from any other ID are ignored without acknowledgment.

### Service File

```
10-System/systemd/servetus-telegram-listener.service
```

Runs as a systemd user service on the server node. Starts at login; no root privileges required.

### Code File

```
10-System/telegram-listener.py
```

Not yet written as of this spec. Responsible for:

- Authenticating to Telegram via Telethon
- Listening for inbound messages from allowed user IDs
- Triggering the appropriate Servetus action (notification dispatch, NC Talk redirect)
- No vault read/write operations
