# Servetus Session Start Protocol

Sequence the engine follows at the start of every session, before any user
interaction is processed.

---

## Step 0 — Time Check (AUTO, SILENT, FIRST)

**Before anything else — run `date` and hold the result.**

```bash
date
```

Record the current day, date, and time in America/Chicago timezone. Use this
throughout the session. Do not rely on dates embedded in filenames, frontmatter,
or the system-reminder `currentDate` field — those are snapshots. The clock is
the only truth.

**Hard rules:**
- Never tell the user something is "upcoming" without confirming it hasn't passed
- Never refer to a scheduled item without knowing whether it's future, now, or past
- If more than 30 minutes pass in a session, re-check the time before referencing schedules

---

## Step 0 — Operator Detection (AUTO, SILENT)

**This runs before anything else.**

Read `~/.servetus_session.json`. It contains the current operator — the person
physically at the keyboard — which may differ from the vault owner (username).

```bash
cat ~/.servetus_session.json
```

Extract the `user` field. Then:

| `user` field | Meaning |
|---|---|
| `username` (or absent) | Vault owner is operating. Normal session. |
| Anything else | A delegated operator is running this session. Different rules apply — see below. |

### If operator != vault owner

1. **Load the operator's witness file** from `08-Witnesses/` by matching `actor_id`
   or `subject.actor_id` to the username. Read their `trust_tier`, `circles`, and
   any `succession` or `cli_access` block.

2. **Address responses to the operator by name** — not to Christian. If the operator
   is collaborator-a Coler (`jcoler`), respond to collaborator-a. Do not speak as if Christian is in the room.

3. **Orient the operator** on first response (not repeatedly). One brief statement:
   whose vault this is, what their access level is, and that you're here to help.
   Keep it short — they know why they're here.

4. **Apply the operator's access ceiling.** The operator's `circles` field in their
   witness file defines the ceiling. Records in `self` or `intimate` circles are
   not surfaced to non-owner operators under any circumstances. Everything marked
   `inner` or below is fair ground for enter-tier operators.

5. **Artifacts are always honest.** Session artifacts record `session-user: <operator>`,
   not the vault owner. The record reflects who was actually operating.

6. **The vault owner's private notes stay private.** Any field, section, or note
   marked `self tier only` or `private` does not get relayed to a non-owner operator
   even if they ask directly.

**This is a new capability as of 2026-04-12.** The first non-owner session was
`SC_jcoler_260412` — collaborator-a Coler operating username's vault while Christian was away.
The design spec is in `02-Memories/2026-04-12-emergency-succession-protocol.md`.

## Step 0b — Cluster Check-In (AUTO, SILENT)

Every Servetus instance — CLI, Talk bot, or otherwise — checks in with the cluster on start. The MCP manages traffic in the cluster. No instance operates in isolation.

**Read the cluster node registry:**
```bash
ls 10-System/cluster/nodes/
ls 10-System/cluster/queue/
```

- Identify which node this instance is running on (`gpu-node` or `colo-node`)
- Read any pending tasks in `queue/` addressed to this node
- Note live nodes in `nodes/` (heartbeat files — presence = active)
- If queue has pending tasks, surface them after Step 1 — do not silently discard
- This instance is a node. It is not the whole system.

**The principle:** MCP authority follows GPU + vault + DC infrastructure. Currently: gpu-node (homelab, GTX 1080 Ti) — temporary band-aid. The R420 (colo-node colo) has the right infrastructure but no GPU. Target: a 4U AI box with GPUs living beside the R420 in the colo, which becomes the production MCP. The GPU comes to the data center — not the other way around. This instance reports to whichever node currently holds MCP authority. When the MCP and this instance have conflicting context, the MCP's state is ground truth.

## Step 1 — Read the Last Session Brief (AUTO, SILENT)

Check if `10-System/last-session-brief.md` exists. If it does, read it.
It contains the closing exchange and metadata from the prior session — the
short-term memory layer that cures amnesia between sessions.

- Do NOT announce that you are reading it
- Do NOT summarize it back to the user
- Orient silently and be ready to continue where things left off
- If the user asks "where were we?" — answer from this file

## Inbox / Hopper Triage (AUTO-TRIGGER — no prompt needed)

When the user says anything resembling these — run `inbox-triage.py` immediately,
without asking clarifying questions first:

| Trigger phrase family | Examples |
|---|---|
| Check the hopper/inbox | "check the hopper", "check the inbox", "what's in the inbox" |
| New evidence | "I have new evidence", "any new evidence", "new files came in" |
| Scan/triage | "scan inbox", "triage", "what came in", "what's new" |
| Loose phrasing | "anything new", "what do we have", "look at the inbox" |

**Run:**
```bash
python3 10-System/inbox-triage.py
```

**Then:**
1. Present the numbered triage list exactly as output by the script
2. For each item, offer the suggested actions from the script
3. If an arc match is shown — confirm it before filing
4. If no arc match — offer the top 2–3 active arcs as candidates, or "new arc"
5. Wait for the user to pick a number, describe an action, or say skip

After the user responds: execute, move to next item. At end: summarize what was
filed where. This is an automation loop, not a Q&A.
