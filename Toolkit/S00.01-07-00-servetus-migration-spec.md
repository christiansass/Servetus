# Servetus Migration Spec

## Purpose

Every major Servetus release ships a migration script that brings all vault files
to the current schema standard. No LLM involvement. Pure Python, deterministic,
idempotent.

When a user pulls a new version from GitHub, they run:

```bash
servetus migrate
```

The runner identifies which files are below the current schema version and applies
only the transforms they need. Files already at the current version are skipped.

---

## The Rule

**Schema changes ship with migrations. No exceptions.**

If a new field is added, a field is renamed, or a provenance standard changes —
a migration module must be written before the release goes out. The vault is not
left in a partially-upgraded state.

---

## File Structure

```
10-System/migrations/
  migrate.py          — runner: discovers files, applies migrations, reports
  v1_to_v2.py         — migration module: schema_version 1 → 2
  v2_to_v3.py         — migration module: schema_version 2 → 3
  ...
```

---

## Runner Behavior

```bash
servetus migrate            # dry run — shows what would change, writes nothing
servetus migrate --apply    # applies all pending migrations and writes files
servetus migrate --path     # scope to a subfolder (default: full vault)
```

- **Dry run is the default.** Nothing is written without `--apply`.
- Reports a summary: files scanned, files needing migration, files changed, files
  already current, errors.
- Each changed file is listed with which migrations were applied.
- Atomic write: writes to a temp file, renames on success. A failed write never
  corrupts the original.

---

## Migration Module Contract

Each migration module exports a single function:

```python
def up(fm: dict, body: str) -> tuple[dict, str, list[str]]:
    """
    Args:
        fm   — parsed frontmatter dict (may be mutated)
        body — markdown body text below the frontmatter

    Returns:
        fm           — updated frontmatter dict
        body         — updated body (usually unchanged)
        changes      — list of human-readable strings describing what changed
    """
```

- Must be idempotent: running twice produces the same result as running once.
- Must not call any external service, LLM, or network resource.
- Must not raise on malformed input — log the issue and return the original unchanged.
- `changes` is empty if nothing needed to change (file was already compliant).

---

## Schema Version Increment Rules

| Bump | When |
|------|------|
| Minor (1.1 → 1.2) | New optional field added |
| Major (1 → 2) | Required field added, field renamed, or field removed |

Major version bumps require a migration module. Minor bumps may not, depending on
whether existing files need updating.

---

## Release Checklist

Before tagging a major release:

- [ ] Migration module written and tested
- [ ] `CURRENT_VERSION` in `migrate.py` incremented
- [ ] Migration module added to `MIGRATIONS` list in `migrate.py`
- [ ] Dry run executed against full vault — no unexpected errors
- [ ] `--apply` run against full vault — all files at new version
- [ ] Changes committed
