## Plain English Goal
Stop the fragmentation and "figuring out" tax. Have a crisp, documented, launcher-supported model so that:
- Hermes is the reliable daily runtime harness (skills, dispatch, voice, persistent agents, home automation, the "shell").
- Grok Build is the high-power contractor tool used *outside* the harness for design spikes, parallel exploration (subagents + worktrees), precise multi-file work, GitHub/PRs, authoring the specs that then load into Hermes.
- The tmux control room (servitus) is the "everything" meta-view when you want all engines visible at once (video-mixer/ATEM model, user as TD).
- Capture, git, and vault sovereignty are non-negotiable for every path.
- Launching the right thing for the job is one or two commands (servetus, servetus-h, servetus-g, etc.).

This eliminates the pain from the originating voice transcript (dormant verbal notes, second-brain activation, multi-engine complexity) by making the model explicit and launcher-enforced.

## Division of Labor (Roles & Explicit Boundaries)
**Hermes Harness (runtime backbone):** Persistent, long-running, HA process execution layer. Skill-driven (servetus-boot + catalog), agent dispatch, voice OS (OpenHome/xAI + prosody + live transcript concierge + headset primary per 2026-06-01 voice backlog), the "shell". Use for: daily verbal processing, agent orchestration (transcription queue, Talk bot, web-concierge, monitors), home automation (HA integration per fork decision), anything benefiting from boot ritual + vault context + persistent profile. Launch: `servetus` (full) or `servetus-h` (quick single-pane). It is *the* daily driver inside Servetus. Vault is sovereign memory (Hermes sessions DB is ephemeral; always export .jsonl).

**Grok Build (contractor / high-leverage design spike tool):** Stateless-per-session (TUI), plan-mode default, parallel subagents in isolated git worktrees (this session is the example; up to 8), precise multi-file edits, long-horizon reasoning, GitHub/PR work, spec authoring. Use for: system design (this exact doc + launcher completion), complex refactors, parallel exploration/gaps analysis, authoring specs/skills that feed Hermes (write to Toolkit/ or 10-System/; Hermes boot loads them), GitHub integration (gh CLI + branch/PR as first demo). Launch: `servetus-g` / `sg`. "Outside the harness" by design during build phase (per GROK.md / servetus skill). Strengths leveraged for Servetus, not in competition.

**Tmux Control Room (meta / "hantainer"):** The everything-visible view (ATEM video-mixer model; user = TD calling shots). 6-pane (Control/Hermes + 4 agents), NEX-T labels, double orange borders, pane-border-format, session-manifest.json + /tmp/servetus-signals.fifo (autonomic boot + real-time nervous system), verbal tmux interface (Hermes translates natural language; never make user type Ctrl+b). Launch: `servetus` (no flag). Control pane = Hermes (per resume + current ~/bin/servetus). Panes are camera feeds/buffers; Control orchestrates. Use when simultaneous visibility/orchestration across engines is the job (e.g., voice dev + PR work + signaling in one view).

**Other engines (Claude Code direct, Ollama bulk, future):** Via `-c` / `-o` for precision or free tier. All under same SERVETUS_VARIANT / SERVETUS_ROOM / capture discipline.

**Handoff patterns (Grok → Hermes + reverse):**
- Grok Build session (on feature branch) authors spec (e.g., new S00.* or dev-backlog), code (10-System/*.py), or skill content → commits (clear messages, timecoded) → (PR or direct to main) → vault update (git pull or Nextcloud sync).
- Next Hermes launch (servetus / servetus-h) or skill reload (`hermes skills list` / boot) sees changes because boot explicitly loads `Toolkit/S00.00-...` + `S00.01-...` order + config/ + references vault paths.
- For Hermes skills that live in `~/.hermes/profiles/servetus/skills/servetus/` (e.g., servetus-boot, servetus-launcher): vault is source of truth (docs + prompts); profile skills are the runtime mirror. Update via handoff (Grok writes vault source; manual or scripted sync to profile for new skills). Never mutate governing docs outside Toolkit/.
- Reverse: Hermes runtime discovers gap (e.g., via voice transcript or Deck) → user invokes `servetus-g` in a pane or external for heavy design lift → Grok returns spec/implementation on branch.
- Capture always first (raw transcript never left in engine).
