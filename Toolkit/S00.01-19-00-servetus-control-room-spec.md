# Servetus Control Room

## Problem Statement

> *"I can't manage what I can't see, and I'm still the MCP."*
> — Christian Sass, April 6, 2026

Right now the human is the Master Control Program. Routing decisions, queue
checks, node health, pipeline state — all of it lives in one person's head,
managed across SSH sessions and log files on a single screen. That is not a
sustainable operating model. The control room exists to transfer MCP duties
from the human to the system.

**Design constraint:** This has to be beautiful enough that you *want* to open
it. Not a tool you tolerate — a cockpit you reach for. The first UI project
worth getting giddy about.

---

## Mental Model

**N8n with a pulse.** Nodes, edges, animated flow, live status badges, file
counts. You glance at it and know the state of the whole system. No SSH. No
log tailing. No holding context in your head.

Think: transparent engine. Not a diagram of the factory — a window into it
*while it's running.*

---

## Design Principles

### 1. Instrument Flight Rules (IFR)

> *"At times when you can't see everything, you have to be able to fly by your
> gauges. You need to be able to navigate this system if you're looking at the
> gauges only."*
> — Christian Sass, April 6, 2026

When visibility drops — one screen, distracted, middle of something else —
the gauges must be enough to fly safely. The control room is not designed for
ideal conditions. It is designed for IFR.

**Implications:**

- **Every gauge has a normal range.** Green is not just "on" — it is "on and
  within expected parameters."
- **Anomalies are unambiguous.** Not a subtle color shift. Something readable
  in peripheral vision.
- **The instruments don't lie.** A heartbeat showing green on a degraded node
  is worse than no heartbeat. Instrument trust is everything.
- **Silence is information.** A gauge going dark means something. The absence
  of a pulse is as readable as its presence. A missing heartbeat must be
  *loud*, not invisible.
- **Minimum viable scan.** Like the six-pack on a real instrument panel —
  what are the six things you need to glance at to know you're okay? That is
  the above-the-fold design question.

### 2. Normal State is Boring

The UI should be visually calm when everything is healthy. Green across the
board, counts moving, pulses steady. The design should only demand attention
when something needs the human. An instrument cluster that's always screaming
is one you learn to ignore.

### 3. It Has to Feel Alive

Not a static dashboard you refresh. Something that breathes. Animated flow,
pulsing heartbeats, files visibly moving through pipeline stages. The
Anthropic thinking animation does enormous psychological work with minimal
pixels — it says *something is happening, trust the process.* This does that
at cluster scale.

### 4. The Gauges Are Also Buttons

> *"You need to be able to interact with the gauges. Push the stop button,
> redirect this to there. It's got to not just be information but control."*
> — Christian Sass, April 6, 2026

Read-only is a weather display. This is a flight deck. Information and control
live in the same surface. See something wrong — reach out and touch it. Stop
that process, reroute that file, drain a queue, flip a node's priority mode.

**Implication for build order:** Phase 2 is read-only, but the interaction
model must be designed in from the start. Gauges that are also buttons cannot
be bolted onto a dashboard that wasn't built to receive them. The control
affordances are architecture, not polish.

### 5. Beautiful Enough to Reach For

This must be something you *want* to open — not a tool you tolerate. The
aviation instrument cluster gives pilots something to be proud of. This
should do the same. Design quality is a functional requirement, not a luxury.

## Presence Spectrum

> *"You are the B-roll of my spoken improvised life."*
> — Christian Sass, April 6, 2026

The control room is not a single interface. It is one system across a spectrum
of presence — the same voice, the same commands, the same Servetus, scaled to
what the user can see and what they need right now. No mode switching ritual.
The interface meets you where you are.

---

### Whisper Mode
Shox headset. Phone in pocket. Eyes free. Voice in, voice back.

Servetus is a presence, not an interface. No screen. No UI. Just the
conversation. Hiking, driving, working a job site, moving through the world.
The system is with you but invisible. This is the gauge you can hear.

*Minimum viable surface: push-to-talk + audio response. Nothing else required.*

---

### Interview Mode
You're thinking out loud. The transcript appears — clean, text only. Like
talking to a thoughtful person across a table who is also taking notes you
can see. Empathetic. Unhurried. The visual layer confirms you are being heard
without demanding your attention.

*Good for: reflection, planning, sensitive conversations, single-screen focus.*

---

### Story Map Mode
You mention a name, a place, a memory — and the canvas moves. Servetus
navigates to it. Relationships surface. Arcs light up. You are not searching.
You are *remembering out loud* and the map is following your mind.

The B-roll plays while you narrate. Your spoken improvised life, rendered in
real time. Watching your own life take shape as you speak it — relationships
appearing, arcs connecting, the shape of things you lived but never saw whole.

*This is the mode that will make people stop and stare.*

---

### Full Cockpit
Everything visible, interactive, animated. Pipeline, nodes, gauges, queue
depth. You are not just recalling — you are operating. IFR instruments and
buttons both. The transparent engine at full resolution.

*Good for: active cluster management, build sessions, system ops.*

---

**Design rule:** These are not discrete modes with a mode-switcher. They are
points on a continuous spectrum. The interface scales to context. The voice
interface is identical across all of them — only the visual layer changes.

## Display Layers

### Layer 1 — Cluster Overview (always visible)

Top bar or sidebar. One card per node.

| Element | Content |
|---------|---------|
| Node name | wordinfilm / binaryranch / macbook |
| Heartbeat | Last seen — green/yellow/red |
| Resource load | CPU %, RAM %, GPU % |
| Active services | badges: whisper / ollama / talk / plex / claude-code |
| Priority mode | Personal ⟷ Cluster (toggle) |
| Quick action | SSH in / restart service / drain queue |

---

### Layer 2 — Pipeline View (center canvas)

N8n-style animated flow. Data moving through the factory in real time.

```
[ Hopper ]──→[ Triage ]──→[ Vault ]──→[ Memory ]──→[ Arc ]
    12              3            ✓            ✓          ✓
  pending        active        filed        distilled   open
```

Each stage shows:
- Count of items currently at that stage
- Last item processed + timestamp
- Animated pulse when something is moving
- Click to drill down into that stage's queue

Stages in the pipeline:

| Stage | What it represents |
|-------|--------------------|
| Hopper | Raw captures waiting — voice memos, Talk messages, files dropped in |
| Triage | Currently being reviewed / routed |
| Vault | Filed to correct location |
| Memory | Distilled to atomic memory note |
| Arc | Linked to an active arc |
| Done | Completed loop — no action needed |

---

### Layer 3 — Drill-Down (on click)

Per node or per pipeline stage. Expands to show:

- What's being processed, by what service, since when
- Log tail (last 10 lines)
- Queue items with status (pending / in-progress / completed / failed)
- Action buttons: retry / skip / escalate

---

### Layer 4 — Open Loops Sidebar

Always visible. Pulled from SOC open loops + cluster queue.

- Count by priority (🔴 / 🟡 / 🟢)
- Top 5 items with owner
- One-click to expand full SOC

---

### Layer 5 — Memory State

What Servetus currently knows it's holding. Not the full vault — the *working
set*: what's been loaded this session, what arcs are active, what witnesses are
open.

---

## Priority Mode Toggle (per node)

Addresses the WordInFilm dual-use problem: personal desktop + cluster node +
Plex server.

| Mode | GPU priority | Cluster behavior |
|------|-------------|-----------------|
| **Personal** | Plex hardware transcoding | Inference queued, not dispatched to this node |
| **Cluster** | Ollama / Whisper inference | Plex falls back to software transcoding |
| **Auto** | Time-based or load-based | MCP decides based on current queue depth and time of day |

The MCP reads each node's mode before dispatching. Heavy inference tasks skip
nodes in Personal mode.

---

## Hopper Gate Control

**Canonical terminology: "opening and closing the hopper."**

- **Hopper closed** — pipeline paused. Files accumulate, nothing is processed.
  You can see the queue fill up without losing control of what runs and when.
  Default state during active development.
- **Hopper open** — pipeline runs. Files move through triage → vault automatically.

This is a first-class control in the dashboard — a single visible toggle, not
a buried setting. The hopper state (open/closed) should be the most prominent
status indicator on the pipeline view. You should never have to wonder which
state it's in.

## Implementation Path

### Phase 1 — Static map (prerequisite)
- Canva or whiteboard diagram of all components and data flows
- Every node, every service, every data path labeled
- Gets the architecture out of one person's head into a shareable artifact
- Input to Phase 2 design

### Phase 2 — Read-only dashboard
- Reads cluster heartbeat files from vault sync
- Reads queue/ and results/ directories
- Reads talk-listener.log and hopper-events.log
- Renders node cards + pipeline counts
- No write capability yet — just visibility
- Stack TBD: could be a local web app (Flask/FastAPI), an Obsidian plugin, or
  a terminal UI (rich/textual)

### Phase 3 — Interactive control room
- Priority mode toggles write back to node config
- Queue management (retry, skip, escalate)
- Service restart via cluster dispatch
- SSH quick-launch per node

### Phase 4 — Live animated pipeline
- Real-time updates via file watch or WebSocket
- Animated flow between pipeline stages
- The transparent engine

---

## Stack Candidates

| Option | Pros | Cons |
|--------|------|------|
| **Web app (FastAPI + HTMX)** | Accessible from any device, one screen or three | Needs a host, another service to manage |
| **Terminal UI (Textual)** | Runs anywhere Python runs, no browser needed | Less visual polish |
| **Obsidian plugin** | Lives inside the vault, zero new infra | Limited animation capability |
| **Electron / Tauri app** | Native feel, full design control | Most build overhead |

Recommendation: start with **Textual** for Phase 2 (fast, vault-native, readable on one screen), then graduate to a web app for Phase 3–4 when the design is proven.
