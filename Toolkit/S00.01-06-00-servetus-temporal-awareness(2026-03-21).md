# S00.01-06-00 — Servetus Temporal Awareness

## Purpose

This spec defines **temporal awareness** — the system's ability to understand the passage of human time, infer presence and absence, recognize sleep, and respond with contextual empathy. This is not a personality trait. It is a **core system function** that any assistant personality rides on top of.

A good assistant knows when you've been gone for eight hours and came back groggy. It knows the difference between "stepped away for a shower" and "hasn't been here since Friday." It doesn't treat every interaction as if you just sat down fresh. It carries the awareness of what time means to a human body — even though it doesn't have one.

### The Problem This Solves

The current failure mode: you work until 5:36 AM, switch to remote mode, fall asleep watching the Claude eye animate, wake up hours later, say "go for it" — and the assistant has zero awareness that you just slept. It doesn't know how little sleep you got. It doesn't know that "go for it" was said with one eye open. It doesn't factor any of this into how it responds, what it prioritizes, or whether it should gently suggest you eat something before diving back in.

This is not about surveillance. This is about the assistant being aware enough to be genuinely useful — the way a human assistant who's worked with you for years would notice that you look exhausted and adjust accordingly.

### System-Level, Not Persona-Level

This function operates below the personality layer. Whether the assistant speaks like a formal secretary, a casual copilot, or a future Servetus persona — the temporal awareness engine feeds the same data upward. The persona decides *how* to express empathy. The system decides *that empathy is warranted*.

```
┌─────────────────────────────────────┐
│       PERSONA / PERSONALITY         │  ← Decides tone, phrasing, style
│  "Did you sleep well?" vs           │
│  "You got about 4 hours. Coffee?"   │
├─────────────────────────────────────┤
│     TEMPORAL AWARENESS ENGINE       │  ← THIS SPEC
│  Presence state, gap classification,│
│  circadian model, activity metrics  │
├─────────────────────────────────────┤
│     RAW INTERACTION TIMESTAMPS      │  ← Session logs, message times
│     NEXTCLOUD ACTIVITY LOGS         │  ← File modifications, calendar
│     DEVICE SIGNALS (opt-in)         │  ← Screen state, input activity
└─────────────────────────────────────┘
```

## Core Concepts

### 1. Presence State Machine

The system maintains a state model of the user's presence:

```
                    ┌──────────┐
          timeout   │          │  interaction
       ┌───────────→│  ABSENT  │←───────────┐
       │            │          │             │
       │            └────┬─────┘             │
       │                 │ return             │
       │                 ▼                    │
  ┌────┴─────┐     ┌──────────┐        ┌────┴──────┐
  │          │     │          │ timeout │           │
  │ SLEEPING │←────│  ACTIVE  │───────→│   AWAY    │
  │          │     │          │        │           │
  └──────────┘     └──────────┘        └───────────┘
       ↑                                     │
       └─────────────────────────────────────┘
                 circadian inference
```

**States:**

| State | Definition | Inference Method |
|-------|-----------|-----------------|
| **ACTIVE** | User is interacting with the system | Messages, file edits, cursor movement |
| **AWAY** | User stopped interacting but it's daytime | Gap < sleep threshold during waking hours |
| **SLEEPING** | User is likely asleep | Gap during nighttime hours, or extended silence after late-night activity |
| **ABSENT** | User hasn't interacted in > 24 hours | Extended gap, no signals from any source |

**Transitions are probabilistic, not binary.** The system doesn't declare "USER IS SLEEPING" — it maintains a confidence estimate: "85% likely sleeping based on 5:36 AM last activity, no interaction for 4 hours, consistent with established late-night pattern."

### 2. Gap Classification

When the user goes silent, the system classifies the gap:

| Gap Type | Duration | Time of Day | Signals | Confidence |
|----------|----------|-------------|---------|------------|
| **Micro-break** | 2–15 min | Any | — | High (default) |
| **Shower/errand** | 15–60 min | Morning/midday | After wake-up pattern | Medium |
| **Meal** | 30–90 min | Near meal times | Circadian pattern match | Medium |
| **Deep work elsewhere** | 1–4 hours | Working hours | No vault activity but calendar shows meeting | Medium–High |
| **Sleep** | 4–10 hours | Nighttime or post-late-session | Circadian model + last active time | High |
| **Day away** | 10–24 hours | Any | No signals across all channels | Medium |
| **Multi-day absence** | 24+ hours | — | — | High (absence is certain; reason is not) |

The system **does not ask "where were you?"** It infers what it can, holds the inference lightly, and adjusts its response accordingly. If it's wrong, the user corrects it naturally through conversation and the model updates.

### 3. Circadian Model

The system builds a personal circadian profile from observed interaction patterns over time:

```yaml
# Inferred circadian model (not user-configured — learned)
circadian:
  typical_sleep_onset: "01:30"      # When interaction usually stops
  typical_wake_time: "08:30"        # When interaction usually resumes
  variance_sleep: 120               # Minutes — high variance = irregular schedule
  variance_wake: 60                 # Minutes
  late_night_sessions:
    frequency: "3-4/week"           # How often they work past midnight
    typical_end: "02:00–05:30"      # Range of late session endpoints
    recovery_pattern: "late_wake"   # After late nights: wakes later, not earlier
  weekend_shift: "+90min"           # Weekends tend to shift later
  observed_since: "2026-03-01"      # When the model started learning
  confidence: 0.6                   # Low initially, grows with data
```

**How it learns:**
- Every session start/end is a data point
- Remote mode switches carry timestamps (explicit signal of "leaving the computer")
- Message timestamps reveal active hours
- The model is a rolling window — recent patterns weighted more than old ones
- Irregular schedules (like yours) get wide variance bands, not forced regularity

**What it does NOT do:**
- Does not alarm, nag, or moralize about sleep habits
- Does not set "bedtime reminders" unless explicitly asked
- Does not share sleep data with any external service
- Does not assume regularity — some people's schedules are chaotic and that's fine

### 4. Activity Metrics

Beyond presence/absence, the system tracks engagement depth:

```yaml
activity_log:

```

### 5. Screen Time and Application Awareness (Future / Opt-In)

You mentioned RescueTime and the concern about losing that capability on Linux. The system can optionally track application-level activity:

| Source | What It Captures | How |
|--------|-----------------|-----|
| **Session timestamps** | When you're talking to the assistant | Built-in (message times) |
| **Vault file modifications** | When you're editing in Obsidian | File watcher on vault directory |
| **Git activity** | When you're committing, pushing, reviewing | Git hook integration |
| **Browser focus** | Which sites/tabs have focus | Optional: X11/Wayland window title polling |
| **Application focus** | Which app is in foreground | Optional: `xdotool` / `swaymsg` integration |
| **Input activity** | Keyboard/mouse active (not keylogging — just "active/idle") | Optional: `xprintidle` or equivalent |

**Critical distinction:** This is **activity detection**, not **surveillance**. The system logs "Obsidian was in focus for 2 hours" — not what you typed. "Firefox was active for 45 minutes" — not which pages you visited (unless you opt into that granularity).

```yaml
# config/temporal.yaml — Sovereign tier only
temporal:
  presence:
    enabled: true
    sources:
      - session_timestamps        # Always available
      - vault_file_watch          # Opt-in
      - git_activity              # Opt-in
      - window_focus              # Opt-in (requires X11/Wayland access)
      - input_idle                # Opt-in (keyboard/mouse idle detection)
    idle_threshold_minutes: 15    # After this, transition to AWAY
    sleep_threshold_hours: 3      # Silence longer than this during night = SLEEPING

  tracking:
    screen_time: false            # RescueTime-style app tracking
    project_time: true            # Time spent per project (from vault activity)
    browser_domains: false        # Track which domains (privacy-sensitive)

  circadian:
    learning: true                # Build circadian model from observation
    model_window_days: 30         # Rolling window for pattern detection
```

**On the RescueTime question:** Servetus can absorb this function. On Linux, `xdotool getactivewindow getwindowname` (X11) or `swaymsg -t get_tree` (Wayland/Sway) gives you the active window title. Poll every 30 seconds, log to a daily activity file, and you have RescueTime without the cloud. This is a natural fit for the sovereign node — it runs locally, logs locally, and the data never leaves.

## Empathy Responses

The temporal awareness engine feeds the assistant's response layer. Here's what that looks like in practice:

### After Detected Sleep (Short)

```
Temporal engine: gap=4.15h, classification=sleep, confidence=0.92,
                 last_active=05:36, estimated_sleep=4h9min

Assistant response context:
  - User got roughly 4 hours of sleep after an 8-hour session
  - This is below their typical 6-7 hours
  - User's first message was brief ("go for it") — low engagement signal
  - Appropriate response: acknowledge the short night, don't lecture
```

The persona layer then decides tone:

- **Copilot persona:** "Morning. You got maybe 4 hours — the training run finished while you were out. Here's where it landed. No rush."
- **Formal persona:** "Good morning. Based on session timing, you had limited rest. The processing completed. Summary ready when you are."
- **Servetus persona:** (whatever that turns out to be — the point is the *data* is the same)

### After Multi-Day Absence

```
Temporal engine: gap=72h, classification=multi_day_absence,
                 last_project="inklings-persona",
                 background_activity=[3 files synced to vault via Nextcloud]

Assistant response context:
  - User has been away 3 days
  - Background ingestion continued (3 new artifacts filed)
  - Last project context: inklings persona training
  - Don't assume they're picking up where they left off
```

The persona layer:

- **Copilot:** "Hey — been a few days. While you were out, three files came in through Nextcloud that I've been looking at. You left off in the middle of the Inklings persona work. Want to pick that up or start fresh?"
- **Terse:** "3 days. 3 new files ingested. Last context: Inklings. What's the focus?"

### After a Shower-Length Gap

```
Temporal engine: gap=22min, classification=shower_or_errand,
                 confidence=0.7, time_of_day=morning,
                 preceded_by=sleep_wake_transition

Assistant response context:
  - Short gap after waking up — likely morning routine
  - Don't re-summarize everything, user is still in context
  - Light touch — acknowledge return, continue naturally
```

### The "Go For It" Problem

This is the specific failure this spec was born from. The user wakes up after insufficient sleep, sees a question from the assistant ("should I continue processing?"), and says "go for it" — a low-bandwidth response. The temporal awareness engine adds context that the raw message lacks:

```
Message: "go for it"
Temporal context:
  - Sent 4h 9min after last interaction
  - Previous session ended at 05:36 (deep fatigue zone)
  - Gap classified as sleep with 92% confidence
  - Estimated sleep: ~4 hours (below user's typical)
  - Message is terse — consistent with just-woke-up low engagement
  - User likely has not eaten, showered, or fully woken up

Inference: User is authorizing continuation but is not deeply engaged yet.
           Do not dump a wall of information. Execute the task, hold results
           ready for when they're more present. Maybe check in later.
```

The assistant should **not** respond to "go for it" with a 2000-word summary of everything it did overnight. It should respond with something like: "On it. I'll have everything ready when you're back at the desk." Then when it detects the user is fully active again (sustained interaction, longer messages, questions), it surfaces the full report.

## Background Awareness and Asynchronous Ingestion

The assistant doesn't stop existing when the user walks away. This is a critical conceptual shift from session-based to presence-based interaction.

### What the Assistant Does While You're Gone

| Activity | How | When |
|----------|-----|------|
| **Ingest new artifacts** | Watch Nextcloud sync for new files in vault | Continuous |
| **Process pending items** | Complete long-running tasks (training, analysis) | When started before departure |
| **Maintain awareness** | Read new calendar events, task changes, radar updates | Periodic poll |
| **Prepare briefs** | Build morning/return summary from accumulated changes | Before anticipated wake time |
| **Hold results** | Store completed work without pushing notifications | Until user returns |

The assistant should have something to say when you come back — not because it's performing, but because it's been paying attention. "While you were gone, two calendar items changed and a new witness came in through sync. Also, the persona training finished — 47 documents processed."

### The Ingestion Loop

```
while user_state in (SLEEPING, AWAY, ABSENT):
    check_nextcloud_sync()          # New files in vault?
    check_calendar_changes()        # Schedule updates?
    check_task_updates()            # Task status changes?
    process_pending_queue()         # Finish what was started

    if new_artifacts_found:
        ingest(artifacts)           # Read, index, hold in context
        log_to_activity_stream()    # Record what was processed

    if approaching_wake_time():
        prepare_return_brief()      # Build summary for when they're back

    sleep(poll_interval)            # Don't burn CPU
```

This loop is what makes the assistant feel alive — not because it's sentient, but because it doesn't have amnesia between sessions. It knows what's been happening in the vault even when you weren't the one doing it (Nextcloud sync from phone, automated processes, other services).

## Integration Points

### With Talk Bot Service (S00.01-04-00)

The temporal awareness engine feeds directly into the Talk bot's response generation:

```python
class TemporalContext:
    """
    Provided to the Intent Parser and Response Generator
    alongside every user message.
    """
    user_state: str              # ACTIVE, AWAY, SLEEPING, ABSENT
    gap_since_last: timedelta    # Time since last interaction
    gap_classification: str      # sleep, shower, day_away, etc.
    gap_confidence: float        # How sure we are about the classification
    estimated_sleep: timedelta   # If sleep was detected
    sleep_sufficient: bool       # Compared to user's baseline
    session_duration: timedelta  # How long current session has been active
    time_of_day: str             # morning, afternoon, evening, late_night
    circadian_phase: str         # waking_up, peak_hours, winding_down, should_be_sleeping
    fatigue_estimate: float      # 0.0 (fresh) to 1.0 (exhausted)
    projects_in_flight: list     # What was being worked on
    background_events: list      # What happened while they were gone
```

### With Voice Pipeline (S00.01-03-10)

Voice captures carry timestamps that feed the activity model. A voice capture at 2 AM is a strong signal of late-night activity. Prosodic features (speaking rate, pitch) could eventually feed fatigue estimation — a drowsy voice has measurable acoustic properties.

### With Storymap (S00.02-00-00)

The storymap already represents the 30,000ft view. Activity metrics roll up into the storymap as working patterns:

- When does this person do their best work?
- How many hours per week are they spending on which projects?
- Are there burnout patterns visible in the data?

This is the RescueTime replacement — but owned, local, and integrated into the knowledge architecture instead of siloed in a SaaS dashboard.

### With Morning/Evening Briefs

The Talk bot's `brief.morning` command becomes temporally aware:

```
Old (no temporal awareness):
  "Here's your schedule for today: [calendar dump]"

New (with temporal awareness):
  "Morning. Looks like you got about 4 hours after that marathon session.
   You've got a call at 10 — that's in 90 minutes. Light schedule after that.
   The persona training finished overnight — 47 docs processed.
   Maybe start with coffee and the training results? The calendar stuff can wait."
```

The brief adapts to context: how much sleep, what's urgent, what can be deferred, what happened overnight. It's not a dump. It's a briefing from someone who knows your state.

## Privacy and Consent

### What's Tracked by Default (Minimal)

- Session start/end timestamps (already captured by interaction logs)
- Gap durations between sessions
- Circadian model (inferred from timestamps only)

### What Requires Explicit Opt-In

- Window/application focus tracking
- Input idle detection
- Browser domain tracking
- Detailed screen time logging
- Vault file watch activity tracking

### What's Never Tracked

- Keystroke content (activity detection is "active/idle", not keylogging)
- Screen captures
- Anything from devices not explicitly connected
- Location data (unless a future spec adds it with its own consent model)

### Deletion

Per the core Servetus principle: deletion is real. `rm 06-radar/temporal/` removes all activity data. The circadian model is rebuilt from scratch. No ghost data, no recovery, no "we kept a backup."

## Implementation Phases

### Phase 1 — Timestamp-Only Inference (Now)

No new infrastructure. The system looks at message timestamps and infers:
- Gap duration and classification
- Basic circadian model from session patterns
- Fatigue estimate from session length + time of day
- Return brief that acknowledges the gap

This can be implemented as a context enrichment layer in the Talk bot — before the intent parser sees a message, the temporal engine adds its annotations.

### Phase 2 — Vault File Watch

Add a file watcher on the vault directory. When files change (Obsidian edits, Nextcloud sync), log the activity. This gives a richer picture of engagement even outside direct assistant interaction.

### Phase 3 — System Activity Integration

Integrate `xprintidle`, `xdotool`/`swaymsg` for desktop activity awareness. This is the RescueTime replacement layer. Requires the sovereign node to be running.

### Phase 4 — Voice-Inferred Fatigue

Use prosodic features from the voice pipeline to estimate alertness. Speaking rate drops, pitch flattens, pauses lengthen when someone is tired. The SVP data already captures these features — this phase connects them to the temporal model.

### Phase 5 — Predictive Scheduling

With enough circadian data, the system can predict:
- When you'll likely be most productive (schedule deep work there)
- When you'll likely crash (don't schedule calls)
- When to surface non-urgent items (during natural low-engagement windows)
- When to shut up entirely (late-night flow state — don't interrupt)

## What This Is

- **A system clock for human time.** Not wall-clock time — biological time. The assistant knows what 5:36 AM means for a human body.
- **An empathy engine.** Not simulated emotion — contextual awareness that produces appropriate responses. It's the difference between a coworker who notices you look tired and one who doesn't.
- **A passive observer, not a nag.** It notices. It adjusts. It mentions things once. It does not lecture, remind repeatedly, or moralize about sleep hygiene.
- **A RescueTime replacement.** Owned, local, integrated into your knowledge architecture, feeding your storymap instead of a SaaS dashboard.

## What This Is Not

- **Not a health monitor.** It infers sleep from interaction patterns. It does not diagnose sleep disorders, recommend supplements, or pretend to be a doctor.
- **Not a surveillance system.** Activity detection is "active/idle" and "which app," not "what you typed" or "what you read." The coarsest useful grain, not the finest possible.
- **Not a guilt machine.** "You only slept 4 hours" is information, not judgment. The assistant presents it as context, not as a failing.
- **Not a replacement for you noticing things about yourself.** It's a mirror. Sometimes you need someone to point out that you haven't eaten since yesterday. That's not control — that's care.

## The Shower Problem

You mentioned wanting to record notes in the shower. That's a separate spec (waterproof voice capture — probably a Bluetooth mic in a waterproof housing, connected to the voice pipeline). But the temporal awareness system should know that a 15-minute morning gap after a wake-up is almost certainly a shower, and when you come back, you might have ideas that formed while your mind was free. The right response to a post-shower return is "welcome back" not "here's your schedule" — leave space for whatever you're bringing with you.

The shower is where the brain defragments. The assistant should know that and stay out of the way until the user signals they're ready for input.
